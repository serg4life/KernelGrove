# Overlays and the build

> Detail split out of `CLAUDE.md`. The index and the cross-cutting rules stay there.

**Overlays.** A `.dtso` is not a new format — 346 of the kernel's 361 use `&label { … }`, exactly what `resolve_label_overrides` already folds onto the real tree — so the whole feature sits on machinery that already existed. `api/overlays.py` does three things over it: build the source from chosen changes, resolve each target against the base, and diff base-vs-applied for the preview. **The assistant is two widgets, and the draft lives in exactly one of them.** `widgets/overlay_panel.OverlayPanel` is the fourth section of the `ActivityBar` ("OVERLAYS") and has three states in the same slot: a *Create new overlay* button, the "select the target node" prompt, and the **preview** — the overlay source as it stands, with *Create overlay file* / *Discard* underneath. `tabs/overlay_tab.OverlayTab` is the central view and shows **the node currently pointed at**. It is **not a permanent tab**: `MainWindow._show_overlay_tab` inserts it at `TAB_OVERLAY` when a draft starts and removes it when the draft is discarded or generated, because a tab that is empty almost all the time invites you into a view with nothing in it. `Ctrl+4` now opens the OVERLAYS *section* of the left panel, which is where the feature actually lives: what it already has, what its binding allows, and *Add new node*. The panel holds no model at all — it renders text and reports which line was clicked; `OverlayTab` owns the `OverlayFragment` and translates that line into a node. So the preview is not a second representation to keep in sync: it is that same draft already written as source, and the ticks are read back out of the draft on every refresh, which is why moving between nodes and back restores exactly what was marked.

The flow: *Create new overlay* → `MainWindow._start_overlay_pick` brings the Editor forward with the last device-tree document (`EditorTab.activate_last_device_tree`) → the user **clicks the node in the source** (`DtsEditor.lineClicked` → `EditorTab.node_clicked`, a plain click, deliberately not a cursor move: a click is a deliberate choice, moving the cursor is not). While that mode is on (`EditorTab.set_node_picking`) hovering paints the **whole node under the mouse** in the accent fill and turns the cursor into a hand (`DtsEditor.set_node_hint`, the block from `innermost_fold_region`) — the same shape as the Ctrl+click include hint, and for the same reason: you see what you are about to pick before you pick it. A node with neither label nor path is not painted, because it cannot be written as a target and the hint has to tell the truth about what the click will do → `OverlayTab.start_draft` resolves that node against the **merged** tree by path (the document's own tree has it half-empty) and the central view switches to Overlays. Clicking a node in the preview retargets both lists and the *Add new node* button (`OverlayPanel._on_preview_click` resolves the click to its node's line with the editor's own `innermost_fold_region`, so a property, the node name and its closing `};` all select the same node; `OverlayTab.select_line` maps that line to the draft by re-parsing the source it just generated — no line map to keep up to date).

`NodeAddition` nests (`children`), because a mux added to a bus can carry devices of its own, and *Add new node* offers `KernelGroveService.list_child_options`: what the node's **bus** admits (`parent_bus`) plus what its **own binding declares inside it** (`schema_compatibles`, the MFD case) — asking only one of the two leaves out half the catalogue depending on the node. **The lists only tick; writing happens in the preview.** Their items carry no `ItemIsEditable` and the trees are `NoEditTriggers`: a property's name belongs to the binding, not to the user, and two places to type the same value was one too many once the preview became editable.

**Creating the file writes it and stops there** (`MainWindow._save_generated_overlay`): into the folder the file explorer has open — the one the user calls their project, which `File → Open folder…` changes — under `<target-node>_layer.dtso` (`OverlayFragment.target_name`, sanitized to `[A-Za-z0-9_.-]`, numbered from `-2` if taken), with no dialog and without opening it in the editor. The node in the name is what tells one overlay from another in a folder with several; with `overlay-1`, `overlay-2`… you have to open them all to find out which is which. Seeing and fixing it beforehand is what the preview was for, and `QFileSystemModel` already watches the disk, so the folder panel shows it with no refresh call.

**Layer 6 is asked for, never ambient — and it belongs to the assistant.** `analyze_source` takes `overlay_base` and `overlay_checks` as *separate* arguments: the base is what makes the merged view and the completion work inside an overlay, and it keeps arriving in the editor; the layer-6 verdict only runs with `overlay_checks=True`, which only the overlay list passes. The reason is that a layer-6 error is uninterpretable where the base is an invisible datum the user never chose — «`&i2c0` does not exist» means nothing until you know *in what*. So the editor keeps the base (`MainWindow._open_explorer_file` attaches `self._overlay_base` to any overlay it opens — `_is_overlay`: the `.dtso` suffix, or a `.dts` carrying `/plugin/`) and says nothing about targets. `_overlay_base` is the merged tree of the last **complete** document analyzed, never of an overlay — for an overlay document `_current_merged_root` is the base with that overlay already applied, no reference for anything else.

**Nothing is written into the overlay to say what its base is.** A `// kernelgrove-base:` marker in the header used to record it; it is gone. The base is asked for at validation time, where the user can see the question and answer it — a comment tied the file to a provenance nobody could see or correct from the interface, and it only ever helped overlays this tool had generated. `MainWindow._resolve_base` still turns a chosen key into a merged tree — open document first (it may hold unsaved changes, and checking against the stale version would lie about what is on screen), then the DB catalogue, then the disk, and finally the same filename inside the open folder, which is what lets a project that moved still find its own base. Results are memoized per key: a folder of overlays sharing one base would otherwise re-parse and re-merge a whole SoC `.dtsi` once per file.

**`widgets/overlay_list.OverlayList` is where that check is run and seen**, and it lives **at the top of the OVERLAYS section of the left panel** (`OverlayPanel`'s idle page), above the *Create new overlay* button — building an overlay, reviewing the ones already written and compiling them are the same task, and having them in two corners of the window meant jumping between them. The central Overlays tab is now only the draft, with a hint pointing at that panel when there is none. The list shows every `.dtso` in the open folder — written by this tool or not, since the assistant steps aside the moment it generates the file and from then on the two are the same thing — with **the base it is checked against** — its name alone, since `loaded:` in front of it repeated a word that tells no base from another, once per row plus the header — and the verdict of the whole engine including layer 6. The targets have no column of their own — in a side panel it ate the width of the filename, and the only actionable thing it said (a target that does not exist in the base) is exactly what the verdict already reports; they stay in the row's tooltip and in the log. Each row picks its own base: a manual choice for that file first, then the loaded tree; nothing is read out of the file itself. *Validate…* acts on **the whole selection** (all rows if none is selected) and asks for the base **once** through `BaseChoiceDialog` — a searchable editable combo, like the SoC selectors, over the open device trees (`open · `), the `.dts`/`.dtsi` of the folder (`local · `) and the entire DB catalogue (`SoC · `, `board · `; ~3.7k entries, which is why it is a completer and not a plain drop-down), plus *From PC…* for a file that is in none of the three. The prefixes are not decoration: the same board can appear in all three, and which one you pick changes what is checked — the open document may hold unsaved changes the file on disk does not. A project has several overlays of the same board; answering the same question once per file is a toll, not a choice. Double-clicking a row opens it in the editor. Its action bar is **two rows**, not one: in a side panel a single row shared between two labels and two buttons squeezed *Validate…* down to nothing, and a button you cannot see is a feature that does not exist. Same cause bites labels there — `_allow_narrow` gives every text-sized widget in that dock `QSizePolicy.Ignored`, so its minimum is zero and **an `addStretch` in the same row takes all of it**: the row saying which base is loaded rendered 0 px wide until the spacer went and the label got the stretch factor instead. No elastic spacers in that dock. Same discipline as the layer it surfaces: with no base at all the column says so rather than passing or failing anything.

**The log is not decoration.** Every explicit validation writes a report naming layer 6, listing each target and where it resolved, and saying *passed* when nothing was found — because «nothing happened» and «nothing was checked» look identical otherwise, and that is exactly the doubt an invisible check leaves behind. `OverlayList` does not display it: it emits `reportReady`, and the report is painted in the **bottom strip, the same one as the diagnostics** (`EditorTab.overlay_log`, page `LOG_OVERLAYS` of `_log_stack`). Two log windows on one screen is one too many, and both answer the same question — «what came out of the last thing that was checked». Which page shows is a selector in that strip's header, and picking the OVERLAYS tool switches to the overlay log on its own (`MainWindow._on_activity_section_changed` → `EditorTab.show_log_page`), switching back to diagnostics on the way out; the severity filter and the counters hide with it, since they say nothing about a validation report, and a *Clear* button appears in their place — the log accumulates reports, while the diagnostics are replaced whole by every analysis and have nothing to clear. The table itself is a folder read, not a live model, so it re-checks on `showEvent` and after the assistant writes a file.

A brand-new node has no "existing properties": it is not in the base yet, so everything it carries is in the added list, `compatible` among them, already ticked.

- **The assistant writes the file once and steps aside.** From then on the text is the model: no parallel in-memory representation to keep in sync, which is why a third-party overlay can be opened, edited and saved without the tool silently dropping what it doesn't understand.
- **An overlay must be told what its base is** (`Document.overlay_base` → `analyze_source(overlay_base=…)`). It cannot `#include` it — that would duplicate the whole tree — so without this the engine is *mute inside an overlay*: measured, `&i2c0 { st…` offers 0 completions with no base and 48 with it. The merged view of an overlay is the base **with the overlay applied** (`preview_overlay`), not the bare base: that is what puts a node the overlay adds at its real path so the other layers can judge it.
- **The scaffold never writes what it does not know.** A new node gets only its `compatible`; emitting the binding's other required properties empty produces `reg = ;`, which is not valid DTS, and inventing a value is worse. What is missing is reported by the engine, with its line — that is its job, and duplicating the list here would rot.
- **A property the user ticks is a different case, and it does get a value** (`_starting_value`). In DT only a `flag` is written without `=`; anything else emitted bare is malformed, which is what ticking used to produce (`label;` for a `string-array`). So a ticked property starts at the first value of its `enum` when the binding enumerates them, otherwise at the empty of its type (`""`, `<0>`) — a visible, editable hole, in the list cell and in the preview alike. A property whose `dt_type` is `None` (it appears with different types in different bindings) still gets nothing: any hole there would be a bet.
- **The preview is editable, and once edited the text wins** (`OverlayPanel.previewEdited` → `OverlayTab.set_source`, debounced 400 ms). The draft is re-read from the source with the ordinary parser — an overlay is a device tree whose root children are `&label` pseudo-nodes, so rebuilding an `OverlayFragment` out of one is a walk, not a second parser — and the lists then show what is written, not what was ticked. Same rule as the editor's, one step earlier, and it is what keeps this from needing two-way sync between a text and a model. Two consequences worth knowing: a later tick recomposes the whole file, so hand-written comments do not survive it (properties, nodes and `#include`s do — the includes are re-read and merged back in for that reason), and a text with no `&target {` block at all leaves the previous draft standing instead of emptying the lists mid-keystroke.
- **The OVERLAYS section is for writing overlays, and only that** (`OverlayPanel._build_idle`). The overlay list is **first**, because it is the content of the section — creating one is what you *do* to it, not the other way round — and it is **collapsible** (`_collapsible_header`): a folder with twenty overlays otherwise eats the whole panel. Each row carries a **toggle**, not a checkbox (`overlay_list.ToggleDelegate`, its own column, drawn by hand like every other icon so it follows the skin): what it says is «this one goes into the build», a setting you leave set, and that is the shape that reads without instructions. It is deliberately **not** the row selection — `checked_paths()` vs `selected_paths()`: selecting is looking, toggling is deciding, and the decision survives clicking on another row. Under it, *Create new overlay*.

- **Compiling is its own section, BUILD TOOLS** (`widgets/build_panel.BuildPanel`, `SECTION_BUILD`), not a block at the foot of the overlay panel. Writing an overlay and building a tree are different tasks at different moments, with different tools. It holds the `.dts` of the open folder (`.dtsi` does not appear — it is a fragment meant to be included, and compiling it alone gives a rootless tree), **single selection** because the one you pick is both the tree that gets built and the base its overlays are checked against, *Add from the database…*, and the two buttons. **Under it, a second list — COMPILED — holds the `.dtb`/`.dtbo` of the same folder**, because what building leaves behind is what decompiling reads back and it used to be reachable only through a file dialog. Two lists and not one mixed: the first list's selection *is* the overlays' base, so picking a binary there would mean nothing. The *Decompile* button acts on whatever is selected there — naming it in its own label — falling back to the file dialog when nothing is (a binary can live outside the open folder, where that list does not reach). Double-clicking a row deliberately does **nothing**: decompiling has a button, and hanging it off the same gesture that picks a row means decompiling by accident while looking. **The folder is watched** (`MainWindow._folder_watcher`, a `QFileSystemWatcher` over the open folder and the subdirectories `OVERLAY_SCAN_DEPTH` reaches): both this list and the OVERLAYS one are disk reads, not live models, and until now they were re-read only on entering their section — delete a `.dtso` or drop a `.dtb` in and nothing moved. The re-read is debounced (`FOLDER_REREAD_MS`) because a build writes several files in a row and each one fires, and re-checking every overlay once per file is work thrown away; it also re-arms the watch, since a new or deleted directory changes what there is to watch. `BuildPanel.showEvent` re-reads too, for what a watcher cannot reach — a network volume, a folder below the depth that gets scanned. **A row brought in from the catalogue carries a cloud** (`icons.cloud_icon`): it is the one thing the filename does not say — that tree is in no path of theirs, it gets written to a temp dir to be compiled and the temp dir goes away, so without the mark someone looks for it in their project and does not find it. The overlays it will include are the ones toggled in OVERLAYS, and this panel **says how many rather than repeating the list** (`MainWindow._refresh_overlay_count` off `OverlayList.checkedChanged`): two places to tick the same thing is one place too many for them to disagree.

- **Building is check-then-compile, in that order, and it is one act** (`KernelGroveService.build_device_tree`). Every toggled overlay is analyzed against the merged tree of the chosen `.dts` with `overlay_checks=True`, and **one ERROR anywhere stops the whole build**; a warning does not, because a warning does not stop the binary being correct. Only then does it call the toolchain: the tree to `<name>.dtb` and each overlay to `<name>.dtbo`, beside their source, which is what `dtc` does by default and what whoever copies them to the board expects. The order is the point — `dtc` knows nothing about bindings and will happily compile an overlay whose target does not exist in the base, so compiling first produces a `.dtbo` that only fails when applied on the board, which is the worst place to find out. The base of the overlays is *the tree being built*: that is what makes the layer-6 verdict interpretable at all (see `checks/overlay.py`) and it is the question you are actually asking when you build. A full tree is compiled **in place** (`compile_source_file`) and not through `compile_overlay`'s temp copy: a `.dts` lives off its `#include "sibling.dtsi"`, and `cpp` resolves that relative to the including file, so a copy in `/tmp` resolves nothing. The `dt-bindings` headers still come out of the DB into a temp dir for the same `-I` reason as before — **and so does every other include that only exists in the database** (`KernelGroveService.materialize_includes`). That one is not an optimization, it is what keeps the tool from contradicting itself: the engine resolves `#include "zynqmp.dtsi"` against the DB, so a `.dts` whose SoC is not on disk merges, completes and validates without a complaint and then died at `cpp` with «No such file or directory» on the very include it had just resolved. Each file is written **at the path its own `#include` names**, not at the key the DB stores it under (`xilinx/zynqmp.dtsi`): `cpp -I` looks for what the directive says. Recursive from there, and a real file next to the source always wins — the user's own `.dtsi` is the one being edited. `MainWindow._compile_to` (Compile and export overlay) calls it too, with no neighbour folder, because there the text goes to a temp copy and nothing resolves on its own. Note this only reaches what the `sources` table holds: a DB built before `finders.iter_source_files` started storing the 77 `.h` that live inside a `dts/` directory still fails on `#include "xlnx-zynqmp-clk.h"` — that one needs `--table sources` rebuilt, not more code. It runs synchronously with the window busy and reports each step as it happens (`on_step` → `MainWindow._log_build_step`, with a `processEvents` so the log moves while it works); `ponytail:` if builds ever get long, that is a `QThread` like `SchemaChecksWorker`.

- **A tree from the catalogue is built by undoing what the database does** (`KernelGroveService.materialize_source`, `MainWindow._build_from_database`). The sources live inside `bindings.db` and `cpp` only reads a filesystem, so the chosen source and everything it includes are written to a temp dir **each at its own relative key** (`xilinx/zynqmp.dtsi`) — flattening them would break the very `#include "sibling.dtsi"` this is reproducing — compiled there, and the `.dtb` copied into the open folder, because inside the temp dir it would be no use to anyone. Nothing is written into the user's project but the binary: a catalogue tree is not a file of theirs, and dropping its source into their folder decides for them where it goes. It writes **any** include the DB holds, not only device trees: a `.dtsi` sometimes includes a header that is not under `dt-bindings` (`#include "xlnx-zynqmp-clk.h"`), and without it `cpp` stops. Those siblings only reach the DB if the ingestion took them, which is why `finders.iter_source_files` now also stores `.h` files living inside a `dts/` directory — 77 of the kernel's 26 891 headers, next to the 1 164 of `dt-bindings`; **an older DB needs `--table sources` rebuilt** or those boards fail with «No such file or directory» in the BUILD log, which is at least a legible failure.

- **The build log is its own page: BUILD** (`editor_tab.LOG_BUILD`, third tab of the bottom strip), and **it reads like the terminal**. What `cpp` and `dtc` said goes in **verbatim** — no indent, no glyph, no dropped blank lines — under the command each was called with, which `_run` records always and not only on failure, the way `make V=1` does. It is written with `shlex.join`, so the line can be copied straight into a shell and run again even when the project folder has spaces in it, and **both** streams are kept, not just stderr: what you came here to read is what you would have seen running it by hand, and there are no two channels there. Dressing it up (the six-space indent and the `ℹ` it used to carry) meant translating in your head between the log and the console. The verdict is the summary line at the end; the layer-6 check step above it is ours, not a tool's, and keeps its own wording. Separate from OUTPUT even though both come out of the same click, because they answer different questions — «did layer 6 pass?» and «what did dtc say?» — and mixing them means hunting for one inside the other. A step reaches the GUI as a `BuildStep` (kind, path, ok, raw messages, diagnostics), never as a formatted line: the wording and the glyph belong to the interface, which is the half that is translated.

**There is no *Export overlay* and no *Compile and export overlay* in the File menu.** Writing an overlay ends in the OVERLAYS section, which puts the `.dtso` in the open folder, and compiling is BUILD TOOLS, which builds the tree with its overlays and leaves the `.dtbo` beside its source: two menu entries doing the same two things by a different route, each with its own Save-as dialog. They took `MainWindow.export_overlay_source`, `MainWindow.compile_overlay`, `_compile_to`, `KernelGroveService.compile_overlay` and the `compile_overlay()` function itself with them — the whole write-the-text-to-a-temp-copy path, which was the one that could not resolve a sibling `#include`. What is left is `compile_source_file`, which compiles a file where it lives.

**Compiling is optional, detected and explained** (`api/toolchain.py`, `api/compile_overlay.py`). `dtc` and `cpp` are never packaged: everything else works without them. Two are needed, not one — `dtc` does not preprocess — and `-@` support is probed by asking the tool, not by comparing version numbers. Compiling also has to **materialize the `dt-bindings` headers from the DB into a temp dir** (`SourcesDatabase.write_headers`), because `cpp -I` can only read a filesystem; the directory is deleted afterwards, and generated overlays emit `#include <…>` rather than pasted header content.
