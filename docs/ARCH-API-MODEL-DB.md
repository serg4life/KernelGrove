# API layer, internal model and database

> Detail split out of `CLAUDE.md`. The index and the cross-cutting rules stay there.

**API layer (`kernelgrove/api/`) — the GUI's only dependency.** The GUI must import from `kernelgrove.api` and nothing else (no `db_manager`, `dt_model` or `dts_engine` imports); the model types are re-exported from `api/__init__.py` for that reason.
- `service.py` — `KernelGroveService`: the facade (list SoCs, load a profile, list connectable bindings, connect/disconnect devices, build the model).
- `dto.py` — `SoCSummary`, `BindingOption`, `BindingInfo`: flat structures so the GUI never sees raw SQLite tuples.
- `database.py` / `socs_database.py` / `schemas_database.py` — read side for the `bindings`, `socs` and `schemas` tables.
- `schema_validator.py` — `SchemaValidator`: runs `jsonschema` over the stored schemas, resolving `$ref`s from the DB through a `referencing` registry. Two entry points: one schema (layer 5) and the `select` ones (layer 2). `typeSize` is deliberately ignored — checking integer width needs values encoded with their real size from a DTB, and from DTS text every cell is 32 bits; `jsonschema` ignores unknown keywords, which is exactly the behaviour needed. `vendor-prefixes.yaml` is pulled out of the per-node loop and answered with one big regex plus a memo: its 966 `patternProperties` were 86% of layer 2's cost and the answer only depends on the property's name.
- `completion.py` — where the cursor is, computed **over the text** rather than the tree: while typing, the last analysis lags and re-parsing per keystroke is not viable. Scanning is local (back to the brace that opens the node), so it costs what the node costs. Strings and comments are masked in place — same length, so offsets still map — because a half-typed `status = "ok` would otherwise unbalance every quote after it.
- `binding_schemas.py` — `BindingSchemaLookup`: resolves a compatible to what its binding says, following the whole `allOf`/`$ref` chain (a Cadence I2C controller declares 14 properties and inherits 48). Implements the engine's `SchemaLookup`, and backs the completion API (`KernelGroveService.suggest_properties`). It replaced `api/bindings_lookup.py`, which read `bindings.document` (raw YAML, no `$ref` resolution) and has been deleted: reading `required` off the raw YAML missed 1 988 entries, `reg` among them in 221 bindings. `property_shape` (not `property_type`) is what the encoder asks: `clock-frequency` is `uint32` in some bindings and `uint64` in others — the type is ambiguous but the shape is not, and the shape is what decides how to encode.
- `soc_loader.py` — rebuilds a tree from the stored JSON and extracts the controller nodes.
- `selection.py` — `PeripheralSlot` (editing state, Qt-free) and the slots → `InternalDeviceTreeModel` translation.
- `git_repo.py` — version control, and the only place that shells out to `git` (via `subprocess`; no library, no new dependency). The model is git's own, handled the way VS Code does: `status()` returns the two groups (**staged** — what goes into the next version — and **changes**), and a file legitimately appears in both (porcelain code `MM`: one modification already staged and a later one that isn't), which is why the two sides get separate diffs — `working_diff(path, staged=True)` is index vs HEAD (`--cached`) and `staged=False` is disk vs index. `stage`/`unstage`/`discard` are per file: `unstage` is `reset HEAD --` (or `rm --cached` before the first commit, where there is no HEAD), and `discard` splits its argument — a tracked file goes back to the index (`checkout --`), an untracked one has no earlier state to return to and is deleted (`clean -fd`). `save_version` commits **only what is staged**. The history is **not numbered**: a commit is named by its short sha and its message. The `v1, v2…` this layer used to hand out were positions in the log invented here, and they matched nothing — not `git log`, not what another person opening the project sees, not themselves once you go back — so they went the moment you could reset to a specific commit and had to be able to name it the way git does. `versions(path=…)` filters that same history by one file. Two ways back, and they are different: `checkout(ref)` is git's own, so it works in both directions — going to an old version to look at it, and returning to a branch. It used to be `checkout <sha> -- .`, content only, so nobody ended up in a detached HEAD «they wouldn't know how to leave»; the objection was right and the answer was not. What was needed was not to hide the operation but to **show where you are** and the way out: `head()` returns a `HeadState` (branch, sha, `detached`), and the panel marks the version you are on. **The way out is the branch label on the graph, and not «back where you came from»** — that was a *Back to `<branch>`* button reading git's `@{-1}`, and it only ever works for **one** checkout: look at a version, then look at another, and `@{-1}` points at a loose sha that git cannot name, so it came back empty and the button had no target. Which is the ordinary way of browsing history, and it left you outside every branch with no way back. So the branches are drawn where they belong: `Version.branches` carries the local branches pointing at each commit, read in the same `git log` pass (`%D` — a label over the graph is not worth a second call to git, let alone one per commit; `_local_branches` drops tags and remotes, which are not places you check out to), `_VersionGraphDelegate` paints them as chips beside the node the way Git Graph and VS Code do, and a version's context menu offers *Check out `<branch>`* for each one, above *Check out this version*. **The chip is filled only for the branch HEAD is actually on** (`_ON_BRANCH_ROLE`, not «this row is HEAD's commit»): while detached, the branch sitting on that same commit is still a branch you are not on, and filling it would say the opposite of what the warning above says. A middle version of this lived for one turn as a drop-down listing the branches — it worked, and it was the same fact stated in a place nobody was looking at. `create_branch(name, ref)` is the other half — *Start a branch here…* on a version's menu: a detached checkout is a place to look, and anything saved there is lost on the way out, so opening a branch at that point is what turns it into a place to work, and it puts a label on the graph where you want it. `versions()` adds `--branches` **when there is no branch**, because `git log` counts from HEAD and a detached checkout otherwise left the list showing only that commit and its ancestors — exactly when you need the later ones in order to go back to one. `reset(sha, hard=…)` moves the branch itself, `--mixed` by default so the files survive as unsaved changes and only the later commits are lost, `--hard` taking the files too (the panel asks with two different texts for exactly that reason). `file_in_index(path)` (`git show :file`) returns the **staged** content of a file, or `None` when there is nothing to compare against, and the module function `changed_lines(before, after)` diffs it against **the text currently in the editor** with `difflib` — not `git diff`, because while you type the file on disk is behind what is on screen and the margin has to talk about what is on screen. The reference is the index and not HEAD because that is VS Code's criterion: staging a change takes it out of the editor margin, which is right — from that point the changes list already describes it as «what goes into the next version», and marking it twice says it twice. Remotes (push/pull), merging, stash and conflict resolution are deliberately out; a conflicted file shows its `U` and can be staged like any other, but there is no merge tool here. Of branches there is exactly what going back needs: a label per branch on the graph, checking one out from it, and opening one on a version — no rename, no delete, no merge.

  **Absent `git` is a normal state, not an error.** `git_available()` is a `shutil.which` check and `find_repo` returns `None` for both "no git" and "not a repo", so nothing needs a `try` around it; only the operations themselves raise `GitError` (`GitMissingError` when git vanished mid-session), carrying git's own stderr, which usually says how to fix it (unset `user.email`, a locked index). Every call is synchronous — local operations of a few milliseconds, triggered by showing the panel or by a click, never by typing.

**Which bindings go in a controller's dropdown.** The devices that declare that bus as their **`parent_bus`** — for an I2C controller you offer an RTC or an EEPROM, *not* other I2C controllers (that would be `child_bus`). Getting this backwards is the bug the first GUI shipped with.

**A connected device can offer its own sub-devices.** An MFD like `ti,twl4030` describes the functions it carries (`ti,twl4030-pwm`, `-gpio`, `-keypad`… 20 of them) inside its *own* binding; they hang off no bus, so `parent_bus` never finds them. `PeripheralSlot.subdevice_parent` holds the compatible whose sub-nodes a slot offers, and `KernelGroveService.list_subdevices` reads them from `schema_compatibles` (same `schema_id`, non-empty `node_path`). It is a separate field on purpose: `child_bus` is a real bus name and the visualizer's colors and `CONTROLLER_LIST` key off it. `PeripheralSlot.accepts_children` is what the tree model now asks instead of `is_bus`.

**Slots nest arbitrarily.** `connect_binding` looks the connected device up in the DB and copies its `child_bus` onto the new slot, so connecting a mux produces a slot that is itself a bus and gets its own dropdown. Hence `PeripheralSlot.is_root` (no parent = a controller of the SoC itself) rather than `is_bus` decides who gets a checkbox: a connected mux needs *both* a checkbox (to enable it) and a dropdown (to hang things off it). Root controllers are only emitted into the model if they host something; connected devices are emitted when enabled, carrying their own children.


**Core internal model — `dt_model/model.py`.** Format-agnostic dataclasses that are the "common language" between parser, DB, and GUI: `DeviceTreeNode` (tree node with parent/child links and DT path), `PeripheralNode` (UI-facing peripheral descriptor), `SoCProfile`, `InternalDeviceTreeModel`. Also holds bus-inference constants (`BUS_TYPES`, `CONTROLLER_LIST`, `RULES`) used by both pipelines.

**Two `BindingsDatabase` classes — don't confuse them.** `kernelgrove/api/database.py` is the **read** side (query methods used by the parser and GUI; it also auto-adds a missing `subsystem` column on connect). `kernelgrove/db_manager/storage.py` is the **write** side. New code should query through `api/database.py`.

**`BindingsDatabase` keeps one SQLite connection per thread (`threading.local`), not one per query.** `extract_connectable_nodes` calls `get_binding_info` once per node while walking a SoC's tree (150–330 nodes on a real one), and `soc_profile_from_tree` runs on every editor analysis — that used to mean hundreds of fresh `sqlite3.connect()` calls per keystroke, each repeating `_ensure_subsystem_column`'s `PRAGMA table_info`. A single connection reused per thread fixes it without a lock: `BindingOptionsWorker` queries the same `BindingsDatabase` instance from its own `QThread`, and thread-local storage keeps that connection separate from the main thread's instead of sharing one sqlite3 object across threads (which sqlite3 forbids by default).

**The database must be self-contained — the kernel checkout is a build-time input only.** Users' machines have no `kernel/` clone, so anything the app needs at runtime has to live in `bindings.db`: the `sources` table stores the full text of every `.dts`/`.dtsi` and every `dt-bindings/*.h` (7.5k files), zlib-compressed (~70MB of text → ~15MB). The `schemas` table adds the processed bindings and their original YAML, also zlib-compressed (3.3MB + 5.0MB), so a full DB lands at 68MB (measured on a full rebuild) — it was 120MB until `socs`/`boards` stopped storing the parsed tree (48MB of uncompressed JSON for something derivable from the source they already point at). `socs.file_path` holds the **relative** key into that table, never an absolute local path. Never add runtime code that reads from `kernel/` — that checkout is gone on a user's machine.

**A document opened from disk resolves its includes on disk first, the database second.** `IncludeResolver.resolve` (`api/includes.py`) takes this as its signal: `base_path` is an absolute filesystem path for a document opened via "Open file" (`EditorTab.open_source` sets `source_key=str(path)`), and a relative key like `xilinx/zynqmp.dtsi` for one opened from the `socs`/`boards` catalogue. Only the absolute case tries the disk — a sibling of the including file — before falling back to the same database lookup as always; a DB-relative `base_path` never touches the filesystem, so this doesn't reopen the `kernel/` dependency above, it only lets a locally-opened `.dts` include sibling `.dtsi`s that never went through ingestion. A locally-resolved source is deliberately **not** cached by `_resolved_source`/`_source_contains` (unlike DB content, keyed by an absolute path so it can't collide with a DB key): it can change on disk mid-session, and the whole point is picking up an edited custom include on the next analysis. Opening such an include from the editor (`MainWindow._open_include`) also gives the new tab its real `disk_path`, so "Guardar" writes straight back instead of forcing "Guardar como…" every time.

Database paths default to `database/bindings.db` next to the repo root in a dev checkout, or next to the executable when packaged (`main._app_root()` checks `sys.frozen`) — `database/bindings.db` is gitignored and must be generated locally, or pointed elsewhere entirely with `KERNELGROVE_DB_PATH`. Before those, whatever the user pointed at by hand (`main.chosen_db_path`, remembered in `QSettings`): if they said «use this one», it is this one. Failing all of those, it falls back to `~/.kernelgrove/bindings.db`: the `.deb` installs into `/opt/kernelgrove`, which is root's, so requiring the DB beside the executable would mean `sudo` for a file that belongs to the user. **And when there is none anywhere, the app goes and gets it** (`db_download.py` + `gui/app.ensure_database`, run before the window). Automatically, with no button to find: whoever just installed the program has no reason to know a separate file is needed or where it comes from. What is on the other side is **static hosting, not an API** — a `manifest.json` saying which version exists and where, and the file — so a bucket or GitHub Releases will do, and `KERNELGROVE_DB_MANIFEST` makes the URL a setting rather than a service: anyone with their own `db_manager`-built database publishes their own manifest and points at it. `MANIFEST_URL` points at the releases of the source repo itself (`serg4life/kernelgrove`). Up to 1.0b3 it pointed at a separate `kernelgrove-releases` repo (before that, `dtstudio-releases`, kept alive by GitHub's rename redirect); that repo stays archived so the already-shipped versions keep downloading their database. The `sha256` is checked and the file is written to a `.part` and renamed at the end: ~68MB over an ordinary network, and half a download weighs the same as a whole one — a truncated database fails much later and far more confusingly than here.

**When that fails** (no network, or no release with a `manifest.json` published), the dialog then offers *Use a local database…* (a file picker, remembered), *Try again* and *Quit*. That is how it has always worked, now as the fallback instead of the only route. `Help → Update database…` and `Help → Use a local database…` are the same two things afterwards; neither reloads in place — the database is held open by several layers with a connection per thread and their own caches, and swapping the file underneath is the kind of thing that half-works, so it says to restart, which is once and is true. Only with no display at all does it fall back to `main._report_missing_database` printing to the console: launched from the applications menu there is no terminal to read a console message in, and clicking the icon looked like it did nothing. This is deliberate, not just a packaging detail: the database is distributed separately from the software (see `packaging/linux/README.md`), and the app is meant to connect to *a* database — the team's own, a customer's self-built one, or a third party's — not necessarily one bundled with the install. `kernel/` is a full Linux kernel checkout used only to build the DB; it is gitignored and is not project code.

`init_sqlite_db` only runs `CREATE TABLE IF NOT EXISTS`, which does **not** alter existing tables — add new columns through `ensure_column`, or an older DB will fail on insert.

## Trap

- **`text_in_includes` memoizes per (file, needle).** It runs on every analysis — that is, on every keystroke — and without the memo it re-parses the whole include chain: ~400 ms per keystroke in a `.dtsi` with includes, more than everything else put together. With it, analysis of that file went from ~400 ms to ~50 ms. The include LRU is also guarded by a lock now, because layer 2 resolves includes from a worker thread.
