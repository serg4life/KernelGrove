# GUI: shape, widgets and theme

> Detail split out of `CLAUDE.md`. The index and the cross-cutting rules stay there.

**GUI shape — the activity bar picks the panel, and nothing else.** Its six sections are Folders, Connections, Source control, Overlays, Build tools and Database. **There was a seventh, NODE TREE, and it is gone**: a second rendering of the same structure the graph already draws and the editor already holds, in a panel that had to be kept in sync with every analysis. Deleting it took `NodeTreePanel` with it and, behind it, everything that only it fed — `DtsEditor.flash_node`, `TreeGraphView.reveal_node` and `_chain_to_path`. **A section never moves the central view** (`SECTION_VIEWS` now holds exactly one entry): they are panels *over the document*, and having the centre jump was the navigation's biggest stumble — opening Folders while looking at the graph threw you back to the text. **What switches text ↔ graph is the panel footer, and only it** (`PanelFooter` → `_jump_to_other_view`), which also records `MainWindow._document_view` — the mode you are working in. Opening a file from the folder panel follows that mode instead of forcing the editor. The two exceptions to «a section moves nothing»: Connections · list is a full-width table and does own a view, and coming back from a full-width view (`_FULL_WIDTH_VIEWS`) returns you to `_document_view`, because otherwise the panel would open beside a view that covers it. **The sections that have a panel share one width** (`LEFT_DOCK_WIDTH`, remembered in `_left_dock_width` and re-read from the dock on every switch): the width belongs to the slot, not to what is inside it. Overlays used to carry a wider one of its own, so the slot jumped on the way in and again on the way out, undoing whatever the user had dragged. The Folders entry in the View menu used to read «Editor», and was renamed for the same reason: it opens a panel, not a view. **The inspector dock only exists where the central view is the editor**, and that hangs off `tabs.currentChanged` (`_on_central_view_changed`), not off the section. It used to hang off the section change, and since a panel section can leave you where you were the two stopped being the same event: any view change that did not go through the rail — closing an overlay draft, a panel footer — left the inspector hidden over the editor or standing over the graph: it shows the node under the *editor's* cursor, so outside it there is nothing for it to show and it would be width spent on «no node». The `QTabWidget` that holds the views keeps its tab bar **hidden** — there used to be two navigations for the same thing and you had to move both to get anywhere. `MainWindow.show_view(tab)` is how the rest of the code switches view: it leaves the rail in agreement, and does *not* move it when the active section already leads to that view (Source control and Overlays both open into the editor, and opening a diff from the versions panel cannot throw you out of Source control). **And it then sets the view, always** — the section no longer drags the centre along, so leaving it to the section would stop this method doing the one thing it promises. It is what the panel footers use (`PanelFooter`, the jump to the other view), which is exactly a request for a view and not for a section. The tab labels passed to `addTab` are deliberately **not** wrapped in `tr()`: nothing shows them; the rail's tooltips and the View menu are what the user reads. **The Database section is not a section at all: it is an action** (`ActivityBar.set_section_action`, `MainWindow.open_database`). Its rail button is not checkable, so it does not enter the group's exclusivity, whatever section was active stays active, and clicking it opens the catalogue as a **floating `Qt.Tool` window** over whatever you were doing — the centre does not move and the panel does not change. That is the point: you look up a board *while* editing something else, and taking the editor away to show a catalogue meant going back afterwards. Same treatment as `PropertyPanel` and the graph's two tool windows (`_show_tool_window`), and the same for `Help → Licenses…`. Sections carry the `Ctrl+1`…`Ctrl+6` shortcuts, in rail order. The catalogue's *Visual graph* button asks for the **view** (`show_view(TAB_VISUALIZER)`) and not for a section: it used to ask for the node-tree section, which since sections stopped dragging the centre did not open the graph at all.

**The iconography is the reference IDE's Material Symbols set, drawn by hand** (`widgets/icons.py`, same `QPainterPath` discipline as before — no resource file, crisp at any DPI, and recolourable). The mapping: `folder_open` (Explorer), `account_tree` (graph — boxes and links, like the cards the graph itself draws), `list` (connections as a list), `alt_route` (source control — two paths, not the old git-branch dots), `dns` (database — two server racks, *not* a disc cylinder: in a hardware catalogue a rack says more), `memory` / `developer_board` (a SoC and a board, in the catalogue cards), `search` (inside every search field), `call_split` / `error` / `warning` / `cable` (the status-bar indicators, which were text glyphs), `add` / `remove` / `fit_screen` (canvas controls, also text glyphs before), `build` / `unarchive` (compile / decompile). The one deliberate departure: OVERLAYS keeps the **layers** glyph instead of the reference's `bug_report` — that slot is labelled "Debug" there and reuses a bug; here the section is Overlays, and a bug icon would read as "report a problem".

**A status-bar indicator is a `_StatusItem` widget, not a `QLabel`**: the strip's foreground changes with the skin (`STATUSBAR_FG` — dark text on accent under `obsidian`), and a hand-drawn icon has to be repainted in that colour; an icon embedded in label HTML would have no way to be recoloured. **Anything holding a baked icon exposes `refresh_icons()`**, and `MainWindow._repaint_theme` walks the widget tree calling it wherever it exists — a list enumerated by hand goes stale the moment someone adds a button with an icon. The card delegate in the Database tab asks `icons` for the same two glyphs instead of repeating the strokes, and caches them by (kind, colour, size) because it repaints per visible row on every scroll.

**`Ctrl+P` opens the command palette** (`widgets/command_palette.CommandPalette`), and there is a search-shaped button for it **centred** in the top strip. That strip is a widget of ours in the menu-bar slot (`MainWindow._build_top_bar` → `setMenuWidget`), with the `QMenuBar` inside it — Qt only lets you put a widget in a menu bar's *corners*, and the design centres it. Centred on the **window**, not on the space the menus leave: an empty counterweight the exact width of the menu bar sits on the right, so the two stretches come out equal (`_sync_top_bar`, re-run on a language change, when the menus change width). With only two stretches the box drifted right by exactly the width of «File Edit View Help». The menu bar is therefore `MainWindow.menu_bar`, never `self.menuBar()`: that accessor would create a second, empty one. It searches **open files, views, actions and the whole DB catalogue** at once, which is the one place you interrupt yourself to reach. It knows none of them: `MainWindow._palette_entries()` hands it a list of `PaletteEntry(title, category, run)` already resolved, rebuilt on every open because the open files and the catalogue change. The filter is substring, not fuzzy — over 3 700 entries a fuzzy match returns anything for two letters. A delegate paints the category right-aligned, because a file and a SoC of the same name are otherwise indistinguishable in the list.

**The status bar carries the reference IDE's indicators**, not just a message: branch, error/warning counts, then the message, then Ln/Col with the node path, the target kernel, the line endings, the file's type and encoding, Analyze and the version. **How many entries the DB holds is deliberately not among them** — it is a fact about startup, not about what is being edited, it does not change all session and nothing acts on it; it lives in Help → About, which is where you go to ask which database you are on. **The type is read off the document** (`file_io.language_of`, by extension): it said `DTS` with a `.json` open, which is the same as saying nothing. **The line endings are a button** (`_toggle_newline`): `Document.newline` is detected when the file is opened (`file_io.detect_newline`), the editor always holds `\n` internally (a stray `\r` renders as a control character mid-line), and `_write_text` puts the chosen terminator back with `newline=""` so Python does not translate anything of its own — the same file saves as LF on Windows and CRLF on Linux if that is what it says. Switching it changes no character of the text but does change the file, so `_refresh_modified_state` compares `newline` against `saved_newline` too; without that the unsaved dot never appeared. Both are refreshed from `_sync_document_bar`, the single point every change of active document goes through — hanging them off the analysis left the strip blank until the first one and describing the previous file after a tab switch. `_refresh_status_items` recomposes them after every analysis and on a language change (they are composed strings, so re-translating a constant is not enough); the cursor is on its own signal (`EditorTab.cursor_moved`) because it is the only one that changes while typing — it used to overwrite the whole status message on every arrow key. **The target kernel is a button there and nowhere else** (`_choose_kernel_target`, `SETTING_KERNEL`): the strip is where the reference IDE puts the language and the encoding, for the same reason — a setting of what you are editing, visible without looking for it and changeable without leaving what you are doing. And it was the question with no home: no `.dts` says which kernel it is compiled for, so it cannot be read off the document, and whoever knows it decides it once for the whole project. Choosing one re-analyzes, because it changes what there is to warn about. **The problem counts come from `EditorTab.diagnostics_changed`, emitted by `_fill_diagnostics`**, not counted independently here: the deferred pass (layer 2 and layer-5 values) lands *after* the analysis and adds diagnostics, so anything that counted at analysis time showed fewer than the list below it.

**The bottom panel is PROBLEMS / OUTPUT / BUILD tabs** with a collapse chevron and no «Show:» label in front of the severity checkboxes, not a drop-down: there are three of them and always the same three, so showing them costs what showing one plus an arrow costs. *Clear* empties whichever log is in front and is hidden over PROBLEMS, where nothing accumulates. Collapsing **hides the stack widget** rather than shrinking the splitter — a `QSplitter` will not go below the minimum of what it contains (~100px for a tree), so "collapsed" used to leave half the list showing.

**The SoC and board selectors live in the Database window** (`tabs/database_tab.DatabaseTab`, a floating `Qt.Tool` window — see the activity-bar note above), not in a strip above the views. They were there, spanning the whole window permanently for something you do when you start working; the strip is gone. The two routes into a document still end the same way — the source opens in the editor and the other views derive from the document being edited — and `File → Open folder…` (`Ctrl+O`) is the third. **There is one way in from the disk, and it is the folder.** *Open from PC…* opened a single file and closed whatever else was open; opening its folder does the same and leaves the rest of the project within reach in the panel — the sibling includes, the overlays, the `.dts` next door — which is what editing a device tree actually involves. Two dialogs for the same thing made you choose between them before knowing what you were about to open. There is no *Open…* button anywhere either: the File menu has it and the empty-window hint names it. The one button on that empty page, *Browse the database…*, carries the same `database` glyph the rail uses for the section it opens, drawn in `ON_ACCENT_COLOR` because it sits on the accent fill (`EditorTab.refresh_icons`, found by `_repaint_theme`'s walk like every other hand-drawn icon).

  **The Database tab is the catalogue, browsable**: a header with **one** free-text search (name, compatible, vendor, path), a row with **two closed drop-downs that are filters, not searches** — vendor and SoC/board — and a list of one card per entry — name, a `SoC`/`Board` badge, four columns (**architecture, vendor, cores, RAM**), the tree's own `model` as the description, its clock, and the two buttons *Load DTS* / *Visual graph*. The compatible and the source path moved into the row's tooltip: they identify the entry, they do not describe the hardware.

  **The same window has the other half of the catalogue: BINDINGS** (`VIEW_TREES`/`VIEW_BINDINGS`, two text tabs in its header). The hardware list answers «what boards are there»; this one answers «what does the database know about this device», which is the question you have while writing a node. It lists every **declared** compatible (25 458, out of `binding_compatibles` — `bindings.compatible` only holds each binding's first one, so listing that table would hide 79% of them), and it **searches in SQL with a cap** instead of loading everything and hiding rows: at 25k entries a search that returns more than a few hundred is the whole list again. **Each catalogue takes its own filter strip with it**: architecture, cores and RAM say nothing about a binding, and neither does «SoC or board», so in their place go the two that do — **vendor and device type** (`_build_binding_filters`, shown when the hardware strip hides). The vendor is the compatible's own prefix and the type is the palette's group, drop-down entries carrying the same glyph the card does. Two strips and not one shared pair of drop-downs because it is another vocabulary: 955 vendors declare a compatible against the 541 that build hardware, and a drop-down whose contents change with the tab has to be re-read every time to know what it filters on. **Both filters are resolved in SQL, with the search** (`_binding_where`, shared by the query and its count), and that is the whole point: what comes back is the first 300 of 25 458, so keeping one vendor's rows *after* fetching them would show only those that fell inside the cut — of `abracon` none, because the cut ends inside the a's. The type goes down as the group's raw subsystems, never as the group's name: that classification is the palette's (`gui/widgets/binding_groups.py`) and the database does not know it. The drop-downs are filled from the database itself — `binding_vendors()`, `binding_subsystems()` — on the catalogue's first open, like the list, and a group with no device in this database is not offered. The «shown of total» that the table's header carried moves up to the search strip, which is the one part that does not hide, and **it counts what is filtered, not the table**: «300 of 25 458» with the filter set to sensors was counting something other than what was on screen, and «300 of 1954» also says the cap is biting. **It is the same card as the hardware list, not a table** (`_EntryDelegate`, told a height and whether it has a footer — the two lists differ in nothing else): a binding has no source to load and no graph to open, so its card ends at the description. What identifies it before you read anything is the **icon of its group in the device palette** (`binding_groups.group_for_subsystem`, the same thirteen curated groups, as glyph and as badge) — a device is looked up here and connected from there, and two classifications for one thing would be two catalogues. Under it, three columns — vendor, the kernel's raw subsystem and the binding that documents it — and the binding's own prose as the description, flattened to one line (`service._one_line`): it arrives from the YAML with newlines and `drawText` would break the line instead of eliding it. The vendor comes from the **compatible's own prefix**, not from the binding row: `aeroflexgaisler,i2cmst` is documented by a binding whose primary compatible belongs to someone else, and reading the vendor off that row said «sifive» about an Aeroflex Gaisler part.

  **Opening one gives `widgets/schema_dialog.SchemaDialog`**, and it exists because of what it replaced: *Open schema* used to dump the processed binding as JSON into an editor tab, which is the database talking about itself — `allOf`, `$ref`, braces — and answers none of what you came to ask. The dialog shows what the Inspector shows of a node, but for a compatible that is not written anywhere yet: the binding's prose, which kernel release it first shipped in, and **every property it admits with the inheritance already resolved** (a Cadence I2C controller declares 14 and inherits 48), required first, each with its type and either its enumerated values or the first line of its description. A `Qt.Tool` window like the other cards, so looking a binding up does not take the editor away.

  **The hardware comes out of the device tree at ingestion, not at display time** (`dt_model/hardware.extract_hardware`, stored in `socs`/`boards` as `arch`/`cores`/`ram`/`clock`/`model` via `ensure_column`). Architecture is the first `cpu@N`'s `compatible`, cores is how many there are, RAM is the sum of `/memory`'s `reg` sizes, clock is the first CPU's `clock-frequency`, description is the root's `model`. Resolving that at display time would mean merging the includes of ~3700 files to paint one screenful of list, so it is precomputed — **which means an existing DB must be rebuilt** (`scripts/build_database.sh`) or the cards show «—» for everything; missing columns are read defensively, so an old DB still lists. A board declares its `/memory` and its `model` but gets its cpus from the SoC `.dtsi` it includes, so `main.inherit_from_includes` walks the `#include` chain by filename over the same walk that already parsed everything, filling only what the file itself does not declare (its own clock or RAM wins — it is the more specific of the two). Coverage on the kernel tree: 3485 of 3682 entries get an architecture, 1208 a RAM, 292 a clock. A `/memory` total under a megabyte is thrown away rather than shown: with `#address-cells = <2>` the cells split and it would read as «4 KB of RAM».

  `extract_hardware` lives in `dt_model` and not in `db_manager` because both sides use it: the ingestion to store it, and the app to label the graph's central card with the tree that is open — the same four rows, computed there on the **merged** root, which is the only one that has a board's cpus.

  The two buttons carry their icon (`document_icon` / `tree_icon`, cached by draw+size+colour like the card glyphs) and are painted by the delegate, so there is no widget to connect: `card_layout(rect)` is the single source of where every piece goes, used by `paint`, by the viewport's click filter and by its hover tracking alike — written twice, painting and hitting would drift the first time someone touched a margin. **The buttons answer to the mouse themselves, not through the row**: the delegate is told which `(row, button)` is under the pointer (`_button_at` → `_set_hovered`, which repaints only the two rows involved and puts the pointing hand on the viewport), the filled one lightens to `ACCENT_HOVER` and the outlined one lifts to `RAISED`. The outlined button is painted with the card's *unhighlighted* background instead of a transparent one — otherwise hovering anywhere on the row tinted the button too, which read as the button activating when it had not. There used to be three boxes you could type into — the search and two editable combos, each over its half of the catalogue — and with three places to type the same thing it was not clear which one to use. Now there is one, and the drop-downs are chosen from, not typed into; the vendor list is built from the catalogue itself, because a DB built from another kernel has other vendors and a hand-written list would both show absent ones and hide present ones. The three conditions are resolved in one pass over the list (`_apply_filter`) — filtering separately would mean three walks and an order the user cannot see anyway. Opening is `socChosen`/`boardChosen` → `MainWindow._on_soc_selected`/`_on_board_selected` → `_open_summary`, whether it comes from a double-click on a card or from the command palette. Cards are painted by a `QStyledItemDelegate` and are not widgets: the catalogue is ~3700 entries, so only what is on screen costs anything, and `_ROLE_HAYSTACK` precomputes each row's searchable text so filtering is a substring test per keystroke rather than four attribute lookups.

**The open-files bar is application-level too**, right under the SoC selector and above the three views: the active document is the one being edited *and* the one drawn in the visualizer, so switching file must not require going back to the Editor tab. **Nothing in the left dock may fix its minimum width.** A `QStackedWidget`'s minimum is that of its widest page, and a button's minimum is the width of its label — «Start version control here» alone held the whole dock at 370 px no matter what `setMinimumWidth` said. `MainWindow._allow_narrow` gives every text-sized control of every page (`_TEXT_SIZED_WIDGETS`) `QSizePolicy.Ignored` horizontally, so the label clips as the panel narrows the way any sidebar's does, and the dock floors at `LEFT_PANEL_MIN_WIDTH` (129 px total). Apply it to any new page added to that stack.

`MainWindow` owns the visible `QTabBar` (`documentBar`); `EditorTab` still owns the documents and hides its own `QTabWidget` tab bar, exposing `document_labels`/`current_document_index`/`activate_document`/`close_document` and a `documents_changed` signal that keeps the two in sync. Changing the active document re-emits `document_analyzed` (analyzing first if that document was never analyzed), which is what makes the visualizer follow the selected tab.
**The Editor has no toolbar of its own.** The strip that used to sit above the text (Save, Analyze, «It is a fragment (.dtsi)», the diagnostic counter) is gone: `Save` was already in the File menu with `Ctrl+S`, the fragment checkbox contradicted the extension for no gain (`Document.fragment` is derived once from the filename, and nothing else should say otherwise), analysis fires on its own while typing so its button is a restart and not the main action, and a counter reading «3 errors» half a window away from the three errors made you look in two places for one thing. So: **Analyze lives in the status bar** (`MainWindow.analyze_button`, `#statusAction` in the QSS — smaller and quieter than a normal button, since the bar must not grow; its colour comes from `STATUSBAR_FG`, not from `TEXT_MUTED`, because under `obsidian` that bar is filled with the accent), and the **counter lives in the diagnostics panel's own filter bar**, which is now that panel's header — together with the selector that chooses what the strip shows, diagnostics or the overlay validation log (see the overlay section below). Anything else that wants to sit above the editor should ask first whether it belongs in one of those two places instead.

**A side panel's footer is one button, the jump to the other view** (`widgets/panel_footer.PanelFooter`, shared), and **what it offers is decided by the central view, not by the panel it lives in** (`MainWindow._refresh_panel_footers`, off the same `tabs.currentChanged`): both footers read *Visualize in node graph* from the editor and *Visualize in DTS editor* from the graph. When the panel decided, opening Folders while looking at the graph offered to take you to the graph — where you already were. **And when the label does not fit, the label goes, not its ending** (`PanelFooter._fit_text`): `_allow_narrow` floors every text widget in that dock at zero, so Qt elided it to «Visu…» beside the icon; the icon alone says the same and keeps its tooltip. It used to also carry the document's device-tree target and the installed `dtc` version, stacked label-above-value; with `_allow_narrow` flooring every text widget in that dock at zero width those rows fell out of line as the panel narrowed, and neither of them was ever acted on from there. The pair shares the object names (`explorerSummary`, `explorerGraphButton`), so it is one QSS rule for both.

**The folder panel indents 18px and draws a guide per level** (`_IndentGuideTree.drawBranches`, `style.EXPLORER_INDENT_GUIDE`). At 12px a file inside a folder barely cleared its neighbour outside it: «is this inside what?» had to be answered by counting. The guides go in `drawBranches` and not in the delegate because the indent is not part of the cell — in a `QTreeView` column 0 starts *after* it, and that band is drawn by nothing else. **And the fold arrow is not in that band**: `drawBranches` deliberately does not call `super()`, `rootIsDecorated` is off, and the chevron is set as the row's own icon (`_GitStatusDelegate.initStyleOption`, `icons.chevron_icon`). Qt draws it in the last step of the branch band, a whole indent to the left of the name and reading as a separate column; worse, a folder has no icon of its own, so its name climbed into the slot where every file's icon is and the two names never lined up. In the icon slot both problems go at once. It has to be the delegate and not `_ExplorerIconProvider` because the glyph depends on whether the folder is expanded, which is the view's business, not the model's. **`.git` is hidden and the rest of the dotfiles are not** (`_HIDDEN_NAMES`): thousands of files nobody edits, and expanding it by accident fills the panel, while `.gitignore`/`.vscode`/`.config` are project content. It hides *rows* (`QTreeView.setRowHidden` on `directoryLoaded`) rather than filtering: `QFileSystemModel` cannot exclude a directory by name, and a `QSortFilterProxyModel` would mean mapping indices in the dozen places that talk to the model. **Selection is `ExtendedSelection`**, and a click with Ctrl or Shift neither opens a file nor folds a folder — it is building a selection. Delete then acts on the whole selection with **one** question for all of it; one per file turns «I marked six and pressed Supr» into six dialogs, which is the fastest way to make someone stop reading them.

**The folder panel creates, renames and deletes** (`FileExplorerPanel._on_context_menu`): *New file…*, *New folder…* on the folder that was clicked (on a file, its parent; outside everything, the shown root), *Rename…* on the row clicked, bound to **F2** and deliberately one at a time (there is no single new name for six files), and *Delete* — on files and on folders, also bound to **Supr**. **A rename is followed wherever the old path was written down** (`fileRenamed` → `MainWindow._on_file_renamed`): the tab that had it open (`EditorTab.rename_document`, or Save would write the old name and resurrect the file), the resolved-base cache, and the two lists of the OVERLAYS section, which are a disk listing and not a live model. **Dragging a row moves it, and a move is a rename with another folder** (`_IndentGuideTree.dropEvent` → `FileExplorerPanel._move_paths`), so it leaves by that same signal and inherits all of it. `setReadOnly(False)` on the model is only there for the drag/drop flags it puts on the rows — the move on disk is deliberately not left to `QFileSystemModel.dropMimeData`, which would do it silently and leave every one of those three pointing at a path that no longer exists (row editing stays shut by `NoEditTriggers`). Dropping onto a *file* means its folder, like the context menu and like any explorer, which is why acceptance is decided in `dragMoveEvent` instead of by the model's flags; only drags out of this same tree are taken (`event.source() is self`) — one from the system file manager would be copying things into the project without saying so. `shutil.move`, not `Path.rename`: a project folder can cross a mount point and there `rename` fails with EXDEV. It does not ask first — the drag is the confirmation, and dragging back undoes it — and what does not fit (a name already taken there, a folder dropped inside itself) is reported once at the end, not once per file. **And what followed had to learn to follow a folder**: `rename_document` matched the exact path, so moving a directory left every tab under it saving to the old tree (`_reapuntada`, on `is_relative_to`), and `_base_cache` is now dropped by prefix. It refuses to land on an existing name — POSIX `rename` overwrites silently, and losing a file by typing a name that was taken is a delete without a question. Both always ask first, and for a folder the question names how many files go with it: «delete `drivers`» and «delete `drivers` and the 143 files in it» are not the same decision. Straight `pathlib`/`shutil` calls, not `QFileSystemModel.mkdir`/`remove` — the model is already watching the disk, so the tree shows the change with no refresh call. **The filter carries `QDir.Hidden`**: a device-tree project has a `.git`, a `.gitignore` and often a `.vscode`, and an explorer that hides them sends you out to a file manager. `.`/`..` stay filtered out — those are navigation, and the tree already navigates.

**Supr is bound twice, and that is only safe because both are widget-scoped.** Two shortcuts with the same key at window level make Qt call it an ambiguous overload and fire *neither*, silently. So the folder panel's delete is a `QShortcut` with `Qt.WidgetShortcut` on its tree, and *Edit → Disconnect device* carries `Qt.WidgetWithChildrenShortcut` plus an `addAction` on the generator tab. `tests/test_gui_smoke.py::test_ningun_atajo_de_teclado_esta_duplicado` counts only window-level shortcuts for that reason — a widget-scoped repeat is a deliberate statement that it is local.

**Nothing in the central stack may fix the application's minimum width.** The bottom panel's filter bar — two tabs, three checkboxes, the counter and two buttons — summed to a 653px minimum, and `QMainWindow` hands the docks whatever the centre leaves: the inspector capped at ~500px no matter how far you dragged, and the only way to widen it was to widen the window. `QSizePolicy.Ignored` on that bar drops the centre's minimum to 239px. Same trick as `_allow_narrow` in the left dock, applied to the container rather than to each child.

- `EditorTab` — several documents open at once (opening an include adds one), live diagnostics filtered by ERROR/WARNING/INFO. Emits `document_analyzed`, which drives the visualizer. Ctrl+clicking **any** include line (device tree or C header — `EditorTab._on_editor_ctrl_click` doesn't filter by type, unlike the visualizer) opens its content in another tab if it's found (on disk next to the file, then in the database): `DtsEditor.ctrlLineClicked(line)` reports where the click landed (the widget itself doesn't know DTS from includes), `EditorTab` matches that line against `document.parse_result.includes`, resolves it with `KernelGroveService.resolve_include` (a single, type-agnostic lookup — deliberately not the merging `resolve_tree`), and emits `include_requested`, which `MainWindow` wires to the same `_open_include` the visualizer's graph already uses. The go-to-definition affordance — underline plus a pointing-hand cursor over the include's target text while Ctrl is held — comes from `DtsEditor.hoverMoved(line, column, ctrl)`, emitted on every mouse move (`setMouseTracking(True)`) and re-emitted on Ctrl press/release so it updates without needing the mouse to move too; `EditorTab._on_editor_hover` locates the target substring within the line (`line_text.find(directive.target)`) and calls `set_include_hint((line, start, length))` — or `None` to clear — since the widget only knows how to draw an `ExtraSelection` underline and swap the cursor, not what a device tree include is.

  **Ctrl+click also goes to the definition of a `&label`**, which is the other half of the same gesture: `ctrlLineClicked` carries `(line, column)` — a line holds at most one include but can hold several references — and `EditorTab._on_editor_ctrl_click` tries the include first, then `_reference_at`, which matches `&label` / `&{/path}` **over the text** with `_REFERENCE_RE`. Over the text and not over the tree because the reference that matters most is the one inside a value (`clocks = <&clk 1>`, `interrupt-affinity = <&cpu0>`), which the parser registers as nothing at all; only the reopening header becomes a node. The hover hint is the include's, reused verbatim — same underline, same hand cursor, and the same reason: you see what you are about to open.

  Resolving it is `MainWindow._go_to_definition` and it happens on the **merged** tree, the only one that knows which file each node came from. That is `DeviceTreeNode.source_key`, set by `IncludeResolver._resolved_source` in the same pass that sets `soc_defined` and, like it, never overwritten by `merge_device_tree` once set — reopening a node with `&i2c0 { status = "okay"; }` is not declaring it, so the key stays the SoC's. The root is deliberately left without one: every file in the chain contributes to `/`, so attributing it to whichever merged first would be a lie. A node whose `source_key` is `None` is written in the open document and the jump is a cursor move; otherwise `_open_source_key` opens that file (a DB key like `xilinx/zynqmp.dtsi`, or an absolute path when the include resolved on disk) and `open_source` reuses the tab if it is already there. Deliberately **not** routed through `_open_node_source`, which the graph uses: that one prefers the `&label { … }` reopening in the open document, which is the right answer for «what does *this* file do to the node» and the wrong one for «where is it declared» — you are standing on the reopening when you ctrl+click it.
- The document bar's close button is drawn by hand (`gui/widgets/tab_close_button.py`, `TabCloseButton`) instead of `QTabBar.setTabsClosable`, whose Fusion-style icon is a low-resolution bitmap. It paints a thin rounded-cap "×" via `QPainter` (crisp at any DPI) and shows a rounded highlight in the same red as unmatched-brace/error styling (`#e06c75`) on hover. `MainWindow._make_close_button` resolves the tab index at click time (`document_bar.tabAt(button.pos())`) rather than capturing it at creation, since closing an earlier tab shifts every later index.
**The inspector is the binding's checklist, not a copy of the source.** It lists **every property the binding declares, written or not** — an `i2c@…` missing `clocks` did not show it, which is exactly when you need to see it — in three columns: name, what the binding says about it — `REQUIRED` (the same green as the `✓ valid against binding` row below, `theme.OK_GREEN`: both say «this is what the binding asks for»), `OPTIONAL` (grey), or `UNNECESSARY` in amber for one that is written and the binding does not declare (amber and not red: the binding may be incomplete, or still a `.txt` that was never converted — but it is the first thing to look at). With no binding resolved at all, no row gets a badge: saying «unnecessary» when nothing could be read would be asserting what nobody said. And the **type** (`property_type_label`: the declared `dt_type`, else the one dt-schema deduces from the name, else the *shape* — `clock-frequency` is `uint32` in some bindings and `uint64` in others, so it has no type but its shape is `scalar`, and the shape is what tells you whether to type `<>` or quotes). The **value** is deliberately not there: it is in the editor half a screen away, and it stays in the row's tooltip. A required property that is missing is named in the amber of the warning below it, which says *which* are missing while the row says *where* — the tint is on the **text, not the background**, because the QSS styles `QTreeWidget::item` and Qt then ignores `setBackground` on a row (measured). Order is «what you must write, what you wrote, what you could write». Clicking a row opens `PropertyPanel`, which offers **only** *Find usages*: *Open schema* dumped the processed binding as JSON into an editor tab, which is the database talking about itself — not something anyone acts on while editing a tree — and it took `service.binding_document`/`schema_document` with it when it went. What replaced it is the readable binding card in the Database window (`SchemaDialog`, above), which is the same question answered instead of dumped. The kernel version goes **inside the card** with its own caption, not appended to the binding's prose, where it read as part of the sentence.

- `VisualizerTab` — the tree as a graph of **node cards** (`widgets/tree_graph.py`). Device-tree includes (`ResolvedInclude.is_device_tree`, i.e. `.dts`/`.dtsi`; a `dt-bindings/*.h` header contributes no nodes) are **fused into the tree**, not shown as a separate node: `KernelGroveService.build_visual_tree` clones `ParseResult.root` and, through `IncludeResolver.resolve_tree` (`api/includes.py`), recursively parses every found device-tree include and merges it into the clone with `dt_model.model.merge_device_tree` — same-named nodes merge their properties (the including file's values win, the include's fill in what's missing) and get their children merged too; new nodes are reparented in. The clone means the editor's and the generator's own tree (`document.parse_result.root`) is never mutated by this. `IncludeResolver` keeps an LRU of already-resolved include trees (handing out `clone()`s, since `merge_device_tree` consumes the source it merges): the same merge now also runs on every editor analysis, and re-parsing a SoC `.dtsi` per keystroke cost hundreds of milliseconds. Only includes that could **not** be resolved still show up as a small "includes no encontrados" package node (red) — there's no legend entry for it (a rare, self-explanatory case isn't worth a permanent legend line), but the color itself is still `COLOR_INCLUDE_MISSING`. The graph starts collapsed one level and expands on click: a real SoC is 150+ nodes, and drawing them all leaves the cards a few pixels wide.

  **A node is a card, not a circle with its name underneath** (the Stitch «editor visual de nodos» design). Fixed 190-wide, a header band carrying the node's name and its semantic colour (SoC / controller / include / connected-from-the-editor — the same colours the circle used to be, now confined to the header so they don't tint the properties), and a body listing up to `GRAPH_NODE_MAX_ROWS` of its properties: name on the left in muted text, value on the right in the accent. `property_rows` strips the DTS syntax for that — `<1>` reads as `1`, `"okay"` as `okay`, and a flag property gets no value at all, because that is what it is; the exact text is the editor's job. The height therefore varies per node, so `node_size(node)` is a module function rather than something the item owns: `_draw` needs it too, to know where each edge starts and ends (bottom edge of the parent card, top edge of the child's — where their connection dots are). There is no separate label item any more, which is also why `GRAPH_HORIZONTAL_GAP` stopped being about "labels not overlapping". `GRAPH_NODE_CORNER_RADIUS` is `theme.RADIUS_ITEM` and is read **at paint time**, never captured into a module constant, so switching skin squares the cards off along with the rest of the window.

  **Fit is honest and stays honest.** Cards are an order of magnitude bigger than the circles, so fitting a wide expanded tree zooms out past readable. That is what fit means, and it is an explicit action; the flow that matters starts collapsed (one card at `GRAPH_MAX_FIT_ZOOM`) and expanding calls `redraw()`, which deliberately does *not* re-fit, so the zoom you were reading at survives.

  **Zoom lives on the canvas, not in the strip above it** (`VisualizerTab._CanvasControls`): a floating +/−/fit cluster pinned to the canvas's bottom-left corner, a child of the view repositioned from `VisualizerTab.eventFilter` on its resize. The zoom is used while looking at the thing being magnified; a button at the far end of the view is the trip that makes everyone use the wheel instead. The strip above keeps only the legend.

  **`&label { … }` / `&{/path} { … }` references are resolved against the merged tree, not left as loose nodes.** The parser itself doesn't know what a reopening reference points to (see `dts_engine/parser.py` below): it hangs each one as a pseudo-node named literally `"&label"` or `"&{/path}"` off the root. `dt_model.model.resolve_label_overrides` runs right after include merging (`KernelGroveService.build_visual_tree`) and cleans this up: it indexes every node by its label, resolves each pseudo-node's reference (by label, or by walking `&{/a/b}` path segments via `find_child`), and folds its content into the real node with `merge_device_tree(..., override=True)` — the override's properties win over what the `.dtsi` already had, since that's the point of a board overriding its SoC (`&i2c1 { status = "okay"; }` must turn the real `i2c1` on, not add a second one). A reference that can't be resolved (typo, or a label outside the merged tree) is left as the old disconnected pseudo-node — better to show the gap than silently drop what the user wrote.

  **The central circle is the SoC package, and only buses or SoC-integrated peripherals with something attached hang off it — never `cpus`, `memory`, `clocks`, or the `/soc` wrapper itself.** `MainWindow._soc_name_for` identifies which SoC the tree being shown belongs to — first by an exact match of the document's `source_key` against `SoCSummary.file_path` (the common case: it's the file that was picked from the "SoCs:" dropdown, or one opened by double-clicking an include, and since ingestion registers essentially every `.dtsi` as a `socs` row, this hits almost always), falling back to a `compatible` match. Either way the label used is `soc.compatible`, never `soc.name` (`name` is filename-derived, not what identifies a SoC). If neither lookup hits, it falls back to the tree's own `compatible[0]` or the document title. Structurally, `build_graph`'s `collect_hoisted` walks the merged tree looking for nodes that are either a bus (`controller_names`, i.e. what `extract_connectable_nodes` already finds anywhere in the tree — i2c/spi/mmc/usb/pci/mdio, regardless of real nesting depth under `/soc`) or a non-bus node with its own `status` property *and* at least one child (a SoC-integrated controller — Ethernet, a UART with its Bluetooth chip — that has something wired to it); it recurses straight through everything else (`/soc`, `/cpus`, `/clocks`, pinctrl config nodes…) without drawing it, so those wrapper/plumbing nodes never appear as graph nodes even though the search passes through them. Once a node is hoisted, its own subtree draws normally (a nested i2c mux still gets picked out as a controller by the same `controller_names` check).

  **The central circle's label depends on whether it's folded: collapsed it reads as the board (what you see from outside), expanded it reads as the SoC (what's inside the board).** `graph_root` always starts `collapsed=True` regardless of `initial_depth` — that param only governs how deep the *bus* subtrees start folded, not the root — and carries both `label` (the SoC name, `_soc_name_for`) and `collapsed_label` (the board name, symmetric `_board_name_for` against the `boards` table). `GraphNode.caption` picks between them; `_on_document_analyzed` computes `board_name` the same way as `soc_name` and falls back to `soc_name` itself when the document isn't a registered board (e.g. a bare SoC `.dtsi` opened directly, where there's no separate "outside" to distinguish).

  **Folding is a dedicated «+»/«−» badge on each node, not a click on the node itself.** It used to be: any click on a node's circle toggled `collapsed`. That broke double-clicking the SoC to open its properties panel (below) — the double-click's *first* press already toggled the fold and re-laid-out the whole graph, so the second press of the gesture landed somewhere else and `mouseDoubleClickEvent` never fired reliably. `_ToggleBadge` (`gui/widgets/tree_graph.py`) is a small child item pinned to each node's bottom-right corner, shown only when the node has children, with its own `mousePressEvent` that toggles `collapsed` and calls `redraw()` — `_NodeItem` no longer overrides `mousePressEvent` at all, so a click or double-click on the circle itself never touches the fold state.

  **The automatic layout is a starting point, not a cage.** Cards carry `ItemIsMovable` and every move is recorded in `TreeGraphView._manual_pos`, keyed by the same `_collapse_key` that already survives a rebuild — the graph is rebuilt on *every* analysis, so without that key each keystroke in the editor undid the arrangement. A `_placing` flag keeps `_render`'s own `setPos` calls out of that dictionary. Edges are therefore drawn **item to item** (`_edge_path` reads the two items' current positions) instead of point to point, and they are re-traced on every move; the block chips of the SoC card became **child items** of it for the same reason — placed in absolute scene coordinates they stayed behind when the card was dragged. The scene rect only ever grows while dragging, or the scrollbars would jump under the mouse. The fourth canvas button (`icons.tree_icon`, the graph section's own glyph) is *auto-arrange*: it empties `_manual_pos` and re-renders.

  **Left-drag on empty canvas is a rubber band, not a pan** (`RubberBandDrag`): selecting several nodes is what a group move or a group disconnect needs, and it is the reason panning moved to the **middle button** (handled in `mousePressEvent`/`mouseMoveEvent` against the scrollbars — `ScrollHandDrag` and a rubber band cannot both own the left button). Qt moves the whole selection when one selected item is dragged, so the group move costs nothing beyond the two flags.

  **Disconnecting acts on the whole selection, and it used to act on the wrong node.** `TreeGraphView.remove_selected` collects the slots *before* emitting anything — each `deviceRemoved` redraws the graph and destroys the items being iterated — and both Supr and the context menu go through it; `Edit → Disconnect device` now routes to whichever view is in front (`MainWindow._disconnect_selected`), since it always asked the Generator's tree and therefore did nothing while looking at the graph. Underneath, `PeripheralSlot.row()` returned **0 for every root slot** (a controller has no parent, so it could not know its own row), which meant `index_for_slot` resolved anything hanging off the second i2c to the first one's index: disconnecting removed someone else's device, or silently nothing when the first controller was empty — the "button that does nothing". The row is now `PeripheralTreeModel._row_of`, which knows the root list and searches by identity (`is`), never `list.index`: two slots of the same compatible under one parent are equal field by field, and `==` on a `PeripheralSlot` walks its parents and children.

  **What the graph can remove is what the open document writes — never the SoC's.** Two different gestures share Supr and the context menu: a device connected in this session is *disconnected* (it is written nowhere yet), and a node the open document declares is *deleted from its source*. The line between them is `GraphNode.editable`, and it is `DeviceTreeNode.soc_defined` — the mark `IncludeResolver.resolve_tree` puts on everything an `#include` brings in — so a board's own `leds`, or the `rtc@68` it adds inside `&i2c0 { … }`, are deletable while `i2c0` itself is not: it lives in the SoC `.dtsi`, which is another file and not the one on screen. Because that node is not `soc_defined`, its `line` is a line of *this* document, which is what makes the deletion possible at all. Two more nodes are excluded on purpose: the central card (it is the whole document) and anything drawn as a `_BlockChip` (those *are* the SoC's controllers, and the chip menu offers no delete). And when nothing in the tree came from an include — a SoC `.dtsi` opened on its own, or a board whose includes could not be resolved — `todo_es_del_soc` turns the whole thing off: with nothing to contrast against, the document's nodes are the SoC's, and the editor is where that file gets edited.

  `api.overrides.node_span(text, line)` is the only new text machinery: the character span the node occupies, opening line through the matching `}` and its `;` (via the parser's own `find_matching_brace`), returning `None` rather than guessing when the brace is orphaned. It returns the *span*, not the patched text, because `MainWindow._delete_source_nodes` applies it through the editor's `QTextCursor` — so **Ctrl+Z undoes it** like any other edit — and bottom-up, since each cut shifts everything after it. It asks first, naming the nodes and the file, and does **not** save to disk: the deletion stays an unsaved change, marked in the gutter like the rest.

  **Everything packaged away is still reachable — double-clicking the SoC circle opens its properties panel, the same way double-clicking the PS block in Vivado opens its configuration wizard.** `TreeGraphView.socActivated` fires on double-click of the root node (`gui/widgets/tree_graph.py`); `MainWindow._open_soc_properties` builds a `SocPackage` (`KernelGroveService.build_soc_package`) — identity plus every node anywhere in the tree with a `status` property, bus or not, drawn in the graph or not — and shows it in `SocPropertiesDialog` (`gui/widgets/soc_properties_dialog.py`). Toggling a controller's status there and pressing "Aplicar" doesn't edit the tree in memory: `MainWindow._apply_soc_overrides` turns each change into a `PropertyOverride` and calls `api.overrides.apply_overrides`, which writes (or updates) a `&label { status = "…"; }` block in the *currently open document's own text* — deliberately the same form `resolve_label_overrides` already knows how to fold back into the real node, so the edit round-trips through reparse → re-merge → override-resolution → redrawn graph without any separate persistence path. It's written straight to `document.disk_path` if the document came from a local file, or falls back to the existing "Guardar como…" dialog (`EditorTab.save_file`) otherwise. This only edits `status`; the rest of `SocPackage` (`name`, `vendor`, …) is informational — editing those would mean picking where in a possibly multi-file merged tree a non-override property belongs, which is a separate, larger change.

  **`SocPackage.name`/`vendor` identify the SoC itself, not the board, and aren't read off the tree root.** The root's own `compatible`/`model` are typically the *board's* ("Raspberry Pi 4 Model B"), inherited from DT convention where the most-specific (board) compatible comes first — showing them under "SoC properties" would be wrong on every board that isn't also its own SoC. `build_soc_package` instead takes `soc_compatible` (`MainWindow` passes `_current_soc_compatible`, the same `_soc_name_for` result already used to label the graph) and splits it on the first comma — `"xlnx,zynq-7000"` → vendor `"xlnx"`, name `"zynq-7000"` — falling back to the merged root's *last* compatible (by DT convention the most generic, closest to the SoC family) only when no resolved SoC compatible is available.
- `GeneratorTab` — the controller/dropdown UI; it only receives a profile via `load_profile`.

`DtsEditor` highlights the brace under the cursor and its partner in green, or in red when it has none — the quickest way to spot which `{` was left open.

**The minimap** (`widgets/dts_editor._Minimap`) sits against the right edge, from the top down, and reserves its width through `setViewportMargins` like the line-number area does on the left. It is placed off the **viewport** geometry and not off `contentsRect()`, or it ends up underneath the vertical scroll bar. It exists for two things and the second is what justifies it: jumping anywhere in a 6000-line `.dtsi` without dragging a scroll bar blind, and **seeing where the things worth looking at are**, over the whole file instead of the screenful in view.

Its marks are laid out the way VS Code lays them out: git changes in a thin strip against the **left** edge (its `minimapGutter.*`, the same values as the gutter's), and errors and warnings as a **band across the whole line** (its `minimap.errorHighlight`/`warningHighlight`), not as an edge tick. The reason shows up in a real file: a change is found by running your eye down the edge and a thin strip is enough for that, while an error has to be visible when you are *not* looking for it, and three pixels at the far edge vanish into the silhouette. INFO gets no band — by far the most numerous severity (which is why it ships off in the filter), and one band each would paint the strip solid. Marks have a 3px floor so a single changed line in a 6000-line file is still findable.

It draws **no text**: at that scale it would not be readable, and rendering it would mean running the highlighter over the whole file on every repaint. One bar per line, as wide as the line is full, gives the same recognisable shape. The per-line height is capped (`style.MINIMAP_MAX_LINE_HEIGHT`) so a short file stays a compact block in the corner instead of stretching into thirty-pixel bands, and the viewport rectangle is painted **first**, under the shape and the marks — on top it covers everything in a file short enough for the rectangle to fill the strip. The shape is recomputed on `textChanged`, not per paint, because the minimap repaints on every scroll.

Diagnostics are sorted **severity first, then line**: in a file with dozens of warnings, one error sorted only by line is invisible.


**GUI layout (`kernelgrove/gui/`).** The window only orchestrates; state and threading live elsewhere:
- `app.py` — `run_app()`: builds the `QApplication`, applies the theme and shows the window. It wires `aboutToQuit` to `stop_background_work` because `closeEvent` only fires on window close — quitting another way would destroy running `QThread`s and abort the process.
- `main_window.py` — `MainWindow`: the three tabs, menus, status bar, and the signals between them.
- `tabs/` — `EditorTab`, `VisualizerTab`, `GeneratorTab`.
- `models/tree_model.py` — `PeripheralTreeModel(QAbstractItemModel)`: adapts the API's slots to Qt; emits `slotStateChanged` on every edit.
- `widgets/` — `DtsEditor` (line numbers, DTS highlighting, diagnostic markers, autocompletion), `BindingDelegate` (searchable device combo), `JsonView`, `DetailsPanel`.
- **Autocompletion**: the editor doesn't know what to offer — it asks whoever set a provider (`DtsEditor.set_completion_provider`), which is `EditorTab`, the only one that knows the document and the bindings DB. The widget only holds the mechanics: show the list, insert what was picked with the value template for its type (`clock-frequency = <|>;`, `clock-names = "|";`, `gpio-controller;`), and emit `completionInserted` so a property with enumerated values can be followed by a second list of those values. It pops up after two characters inside a node whose compatible is known, and `Ctrl+Space` forces it.
- `workers.py` — `BindingOptionsWorker` (DB lookups off the UI thread) and `SchemaChecksWorker` (the deferred pass after each analysis; carries a token identifying the text it checked, so a result that arrives after the document changed is dropped instead of pinning warnings on the wrong lines).
- `widgets/git_panel.py` — the third section of the `ActivityBar` ("SOURCE CONTROL"), on top of `api/git_repo.py`: the two change groups in one `QTreeWidget`, a message box with presets (`Peripheral added`, `Clocks adjusted`…) plus **Save version**, and the version list below. Clicking a file opens its diff for the side it is on; clicking a version opens the whole commit. **A version row is its message and nothing else**, and the history is drawn as a graph: `_VersionGraphDelegate` paints a vertical line with one node per commit down a 20px gutter — Git Graph's shape, which is how a history is read — and the version you are on is the filled, slightly larger node plus a bold row. It replaced a «● » of text glued in front of the message, which was a glyph of the UI font and therefore the size of the text for what little it said. The short sha went with it: nothing here is typed, you click the row, while the message is the only thing that tells two versions apart at a glance and in a narrow panel those seven characters were eating it. It is still in the row's tooltip and in the summary line above. Not a colour either: in this panel colour already means a file's state, and «where am I» has to read under any skin and any colour vision. A commit's context menu offers the three ways back described above — *Check out this version*, *Reset here, keeping the files*, *Reset here and discard the files* — each asking first, with the text spelling out what is lost in that particular one. **Each change carries its own buttons, in its own row** (`_row_actions`, a widget in a second column that fits its contents while the name column stretches) — VS Code's gesture: what you can do with a change sits next to it, instead of selecting first and then hunting for a shared bar. Which buttons depends on the group: staged offers only unstage `−`; unstaged offers discard `↺` and stage `+`. The same three still act on the **selection** from the context menu, where selecting a group row counts for all its files. The **Save version** button sits *below* the message box at full width, not beside it: `MainWindow._allow_narrow` floors every text widget in that dock at zero, so on one row the stretched combo ate the button whole and it was simply not there. Discard only offers itself for unstaged changes (to undo something already staged you unstage it first, so "discard" always means the same thing) and asks first, listing the files, because nothing recovers them. Saving with nothing staged offers to include every change rather than failing on git's `nothing to commit`. It renders the three states rather than failing on them: no `git` installed (the panel says so and shuts itself down), a folder not under version control (a *Start version control here* button — `git init` is never automatic, that would create repositories by surprise), and a working repository. The branch name is shown even though the panel has no branch operations: whoever opened a folder that already was a repository of theirs needs to see where a save is going to land. `showEvent` re-reads the state, which is what replaces watching the disk — save in the editor, switch to this section, and what you see is current, with no `QFileSystemWatcher` or background timer. **Coalesced to one read per switch** (`_schedule_refresh`, a `QTimer.singleShot(0)` behind a pending flag): entering the section fires two `showEvent`s — one when the stacked widget changes page, another when the whole column becomes visible again — and each was a full `git status`, so the same switch paid for it twice. **And re-reading does not mean repainting**: `refresh` keeps the `(status, versions, branch)` it last drew and returns early when they come back equal (`RepoStatus` and `Version` are `dataclass(frozen=True)`, so `==` is structural). Repainting is the expensive half — one row per file, each carrying its two buttons as real widgets (`_row_actions`), so a tree holding a mass rename is 500+ widgets built, ~120 ms, and it was rebuilt from scratch on every visit even with nothing changed. `FileExplorerPanel.set_git_status` bails out on the same test, for the same reason: recomputing the tinted folders is a `Path(...).parents` per changed file. Measured on a tree with 243 changes: entering the section went from ~190 ms to ~60 ms, of which git itself is ~20.

  **The folder panel is decorated the same way** (`file_explorer._GitStatusDelegate`): the file's name tinted plus a letter at the right edge, VS Code's two marks for the same reason — the colour is read at a glance and the letter says which state it is. The letters are VS Code's, not `git status --porcelain`'s: what git calls `?` shows as **U** (untracked) and what git calls `U` shows as **C** (conflict). A folder containing something changed is tinted too, without a letter (the folder is not modified, something inside it is) — otherwise a project that keeps its overlays in `overlays/` shows nothing until you expand it. The badge lives in a delegate and not glued to the file name because this dock narrows to zero (`_allow_narrow`): glued to the name it would be the first thing elision eats, exactly when the panel is too narrow to read names and the letter is all that is left. `GitPanel.file_status()` is the single source (unstaged wins over staged: what is on disk now is the later change). **It is fed when the disk changes, never on every analysis**: it used to ride along in `MainWindow._mark_git_changes` on the grounds that it was the same moment and came for free, and it did not — a full `git status` per analysis, i.e. every time you stopped typing for 600 ms, which is ~200 ms of blocked UI on a repo the size of a kernel checkout (6 ms on an ordinary project — the cost is the repo's, not the panel's). It also answered a different question: the tree paints what is on **disk**, and typing does not change that. So now it is repainted by `MainWindow._refresh_git_decoration` on save (`EditorTab.document_saved`, emitted from `mark_saved`, the one point every save route goes through) and on opening another folder, plus `GitPanel.statusRefreshed`, which hands over the status the panel has *already* read in its own `refresh()` rather than paying for a second one.

  **The editor's own change bar comes from here too.** `GitPanel.line_changes(path, text)` is what `MainWindow._mark_git_changes` calls after every analysis, and `DtsEditor.set_change_lines` paints at the left edge of the gutter, **with VS Code's own criterion** since that is where the gesture is learned: **green** for an added line, **blue** for a modified one, and a small **red triangle** at the junction where something was deleted (a deletion occupies no line of the current text, so there is no bar to paint and the different shape says by itself that this is not "a changed line"). The colours are its `editorGutter.addedBackground`/`modifiedBackground`/`deletedBackground` (Dark Modern), all clearing 3:1 on the gutter background.

  Blue for "modified" is the one choice that surprises and it is deliberate: amber is WARNING everywhere else in the editor — line number, line background, minimap band — so a touched line and a line with a warning read the same. The width is VS Code's too, 3px: what made the old bar invisible was never the thickness but the colour, and with the saturated green and blue 3px reads fine and leaves the line number its room. Only the deletion triangle has a size of its own (`EDITOR_CHANGE_DELETED_SIZE`), because it is the one mark recognised by its shape rather than its position and at 3px it would be a speck.

  The classification is `difflib`'s and lines up with VS Code's `LineChange` by construction: `insert` → added, `replace` → modified, `delete` → the triangle. So replacing 2 lines with 3 comes out entirely blue, not blue plus green, in both. Only the gutter, never the text background — half the screen tinted because it is unsaved would bury the diagnostics, which are the thing you actually have to see. A file with no path, outside the repo, or not in any version yet gets no marks: painting a brand-new file entirely green says nothing the changes panel does not already say.
- Diffs open through `EditorTab.open_source(..., read_only=True)`: `DtsEditor` takes a `highlighter` parameter (`DiffHighlighter` instead of `DtsHighlighter`) and `_save_document` refuses a read-only document, so a diff can never be written over the file it describes. Their title ends in `.diff`, so `is_device_tree` is False and the semantic engine ignores them.
- `theme.py` — the design system, and there are **five skins over one stylesheet**. All three fill the *same* set of token names, which is the vocabulary the QSS speaks, so no rule belongs to only one of them. **A skin is a palette and nothing else.** Radii, paddings, font weights and caption sizes are module constants (`RADIUS_PANEL`/`RADIUS_CONTROL`/`RADIUS_ITEM`, `BUTTON_PADDING`, `BUTTON_WEIGHT`, `PRIMARY_PADDING`, `HEADER_SIZE`, `TAB_PADDING`), the same for every skin and set to «Obsidian Deep»'s values — square containers, 2px only on the small things you press. They used to live in each skin's table, so switching theme moved buttons, fattened tabs and rounded corners: two different things behind one switch. `tests/test_gui_smoke.py::test_las_pieles_solo_cambian_la_paleta` asserts the shape is identical across the three and the palette is not. `style.py` holds what QSS cannot reach (colors used by `QPainter`/`QTextCharFormat` — the graph, the syntax highlighter, the minimap — plus sizes set in code) and derives them from `theme`'s tokens. **No widget carries a color or a corner radius of its own.**
  - **`classic` is the default and is the system the app grew up with**: four surfaces in a fixed order (`SUNKEN` content, `APP` frame, `PANEL` side panels and bars, `RAISED` what you click), 1px lines to separate them, 3px radius on controls and 6px only on what floats, dioxazine purple as the accent, compact buttons. Dark only — it never had a light mode, and inventing one would be designing a new theme rather than keeping the one that existed, so picking `classic` pins the mode to dark and the light/dark entries go disabled.
  - **`site` is the landing page's stylesheet applied literally** (the landing page no longer lives in this repo; its tokens are transcribed in `theme.py`): its eight tokens verbatim in light and dark, two backgrounds and a single `--border`, 12px cards, 9px controls, accent-filled primary buttons, `--accent-text` for the accent *on* a background, `ACCENT_FILL` as the mockup's `color-mix(accent 14%)`. It is the brand image; on screen it reads airier, more page than IDE.
  - **`obsidian` is «Obsidian Deep», the Stitch `DESIGN.md` for the node window**: the classic skin's four-surface structure filled with that system's `surface-container-*` ramp in neutral grey (`#131313` content → `#1b1b1c` frame → `#202020` panels → `#2a2a2a` what you click), **square corners** (0px on every container, 2px only on the small things you press), and Material 3's purple for what is active — `primary` `#d8baff` as the fill with `on-primary` `#3d2163` as the text on it. The brand dioxazine `#53377a` is that system's `primary-container` and fills nothing here: at 1.7:1 over the background neither the active tab's rule nor the activity bar's stripe would be visible, which is exactly what the system asks to mark with it. Dark only, for the same reason as `classic` — its palette *is* a dark M3 scheme and a light mode would have to be invented. Two things the sheet already did for it: the 2px accent bar on the active tab and on the checked activity-bar button, and 1px lines instead of padding between zones. One thing it did not: **the status bar is filled with the accent** under this skin and only this one, through `STATUSBAR_BG`/`STATUSBAR_FG`/`STATUSBAR_HOVER`. Those three are read with `tokens.get(..., APP/TEXT_MUTED/HOVER)` rather than added to the other tables — the rule is that no QSS rule belongs to one skin, not that every skin has to spell out a default it already has. Anything dropped into that bar has to take its colour from those tokens (`#statusVersion`, `#statusAction`, `QStatusBar QLabel`, and `QSizeGrip`, which the native style would otherwise paint in the window background).
  - **The logo is not part of the skin either** (`gui/brand.py`, `gui/brand/*.svg`, copies of `brand/logos/`). It is the window icon — which is also what the About box shows — and the wordmark on the empty editor, the one screen that can afford it. The mark is the **sprout** — a trunk that opens into two nodes — and the geometry is the same as the landing page's (`brand/logos/`, same `viewBox="96 106 320 320"`), so the two cannot drift apart. Both files are rasterized from the SVG at use time with **two** colours swapped: the brand black (`#0a0a0c`), which is the wordmark, becomes the active ink, and the purple of the sprout becomes the brand's own pair (`#612e81` light / `#c187d4` dark) — the dioxazine sits at 1.96:1 on the dark background, the same defect `obsidian` documents for `#53377a`, so leaving it alone would make the logo invisible in the mode the app ships in. The purple *in the file* is a third one, `#8b5cf6`, balanced at 4.2:1 on white and 4.4:1 on black, because the same file is also copied verbatim where the background is unknown: the `.deb` icon, the `.desktop` entry and `packaging/windows/kernelgrove.ico` (regenerated by `scripts/build_icon.py`, which rasterizes each of the seven sizes separately from the SVG — reducing one 256px PNG smears the sprout at 16). `EditorTab.refresh_theme` redraws the wordmark on a skin change; the window icon is set once in `run_app`, after the theme, so the first window shown already carries it. **On GNOME that window icon is not what the desktop shows**, though: the shell matches the window to an installed `.desktop` through the app id (`setDesktopFileName("kernelgrove")`) and takes the icon from there, falling back to the theme's `application-x-executable` — a cog under Yaru — when there is no such entry. So the icon in the dock and the switcher comes from the `.deb` (or from `scripts/install_desktop_entry.sh` when running out of a checkout), and the desktop file's basename, its `Icon=` and the app id have to agree; change one and you change all three.
  - **The font is not part of the skin.** Inter ships with the app (`gui/fonts/`, five static weights 400–800, SIL Open Font License 1.1 with its `OFL.txt` alongside as the licence requires; declared as package data) and is used by both. Loaded with `QFontDatabase.addApplicationFont` in `run_app` **before** the stylesheet, since QSS names the family and Qt will not re-resolve it later. Not linked from Google Fonts: a desktop app cannot depend on the network to look right, and should not call a third party on startup.
  - **Skin and mode are both live** (`View → Appearance`, `SETTING_SKIN`/`SETTING_THEME`). `theme.set_mode(mode, skin)` swaps the table and calls `style.refresh()`; `MainWindow.apply_theme` re-applies palette and stylesheet. Mode is **light or dark, and nothing else**: following the desktop (`QStyleHints.colorScheme()`, Qt's `prefers-color-scheme`) is gone, and so is the *Match the system* entry. It was a third state that decided which of the two you actually saw, so picking «Light» or «Dark» read as correcting the system rather than as choosing. The default is dark; a `SETTING_THEME` left saying `system` by an older version falls back to dark in `set_mode`, which is what it resolved to on most machines anyway. **Nothing may capture a color at import time**: a module-level `COLOR_X = style.Y` freezes whatever was active at startup, which is why the graph, the editor and the palette read `style.X` at use time and `binding_palette`'s sheets are functions, not constants. What still needs an explicit nudge is whatever `QPainter` already drew: `MainWindow._repaint_theme` calls `retranslate()` (rebuilds the activity-bar icons, redraws the graph), `Card.refresh_skin()` on every card, and `DtsEditor.refresh_theme()` (rebuilds the highlighter's `QTextCharFormat`s, made once at construction).
  - `widgets/card.Card` is the mockup's bordered card with its title bar and monospace filename, used by the Inspector and the properties panel. The mockup's three window dots are **not** in it: on the landing page they say «this is a code window» to someone who has not installed anything yet, and inside the application — where you are already looking at one — they say nothing and eat the width of the name. **It draws itself under every skin**, for the same reason the radii are shared: the shape of the application is one, and only the palette changes. It used to appear only under `site` and collapse to a bare container under `classic`, which meant changing theme moved the contents of two panels. What survives in both is the row treatment the mockup introduced: monospace rows, muted labels, and `required` marked in `--accent-text` inside the row (the mockup's `<em>`), plus the green `✓ valid against binding` (`#2fb673`) shown **only** when there is a binding and nothing of it is missing.
  - **Syntax highlighting is part of the skin too.** `style._PAIRS` is One Light/One Dark — what the app always had, and what `classic` and `site` still use — and `style._SKIN_PAIRS` overrides the handful of names that change per skin (`obsidian` in its M3 purple family, `contrast` saturated against pure black/white, `colorblind` in Okabe-Ito). Inheriting them was contradicting the skin: the high-contrast one painted code in the same mid tones as everything else, and the colour-safe one put One Dark's green strings on screen next to the error red — exactly the pair it exists to separate. Only the names that differ are listed; the rest fall back to `_PAIRS`.
  - **A `QWidget` subclass does not paint the background or border the stylesheet gives it** unless it sets `Qt.WA_StyledBackground` (a plain `QWidget()` instance does; a subclass does not). `ActivityBar`, `Card` and `PanelFooter` set it for that reason — without it the activity bar rendered in its parent's colour, so the icon rail and the left panel were the same tone with no line between them, which is precisely what `EDGE` exists to draw. Set it on any new `QWidget` subclass that carries an `objectName` with a background or border rule.
  - Semantic colors (error, warning, success) are a separate family and never compete with the accent. Neither does the **teal** that marks "comes from the editing session, not in the `.dts` yet" (`style.COLOR_GENERATED_BRIGHT`): that marker has moved three times, each time because of a collision — yellow clashed with WARNING, purple stopped working the moment purple became the brand accent, since a generated node and a selected one cannot share a color.
  - **`palette()` is not optional.** QSS does not reach what the style itself draws — a checkbox's tick, a combo's arrow, a tree's branch indicator. Those come from the `QPalette`, and without it they keep Fusion's defaults. `apply_theme` sets the palette first and the stylesheet second. **And never style `QComboBox::drop-down`**: styling that subcontrol switches the whole widget to QSS rendering, so the native arrow stops being drawn and only a `::down-arrow` with a real `image:` would replace it — the CSS trick of a 0×0 box with borders renders as a square in Qt, not a triangle. A `border: none; width: 20px` rule was there, and the result was that *no* drop-down in the application showed its arrow: every combo looked like a plain text field.
  - **What Qt cannot do, and is therefore not there.** The site's `transform: translateY(-1px)` on button hover (QSS has no `transform` — the primary button lightens its fill instead, precomputed because QSS will not compose `opacity` over a solid one), `backdrop-filter`, `color-mix` at runtime (`theme._mix` precomputes it), and `prefers-reduced-motion` (Qt exposes no such hint; the app has no animations to disable — tree expansion animation is already off).
  - **`contrast` is high contrast, light and dark.** Not a brand skin: the one you pick when the rest cannot be read. Text reaches 7:1 (WCAG AAA) on all four surfaces, the zone edge 3:1, and the surfaces step 5 points of L* instead of the 2 the aesthetic skins use, so zones separate even where no border is drawn. Yellow on black / deep blue on white for what is active, the way the system-level high-contrast themes do it.
  - **`colorblind` is the colour-vision-safe skin, light and dark.** What changes is not the surfaces — ordinary cool greys — but the three colours that *mean* something. Measured with the Machado (2009) simulation matrices, the ordinary red and green of ERROR and OK land at ΔE 12 under deuteranopia: the same colour for one man in twelve. Here they come from the Okabe-Ito set and no pair drops below ΔE 25 under any of the three dichromacies. **The warning is violet, deliberately**: amber is the convention, but the only amber dark enough to read on a light background falls to ΔE 3 against the vermillion of the error. The editor's change bar follows the same three (`change_added`/`change_modified`/`change_deleted`, `.get` tokens defaulting to VS Code's green/blue/red) — added-green and deleted-red are exactly the pair that vanishes, and blue for "modified" collapses onto the green under tritanopia.
  - **Qt ignores `em` (and `%`) in `font-size` — only `px` and `pt` work.** The sheet had fourteen relative sizes and *not one of them applied*: every caption, badge and section title was silently rendering at the base font, which is why the panel headers read as full-size bold text. They are still written in `em` in the template — that is the legible unit — and `stylesheet()` converts them to `pt` against `QApplication.font()` (`_EM`, `_em_a_pt`, with a 6pt floor). So they stay relative to the desktop's font, which was the point, instead of being nailed to pixels. Verify a new `font-size` actually took: read the widget's `font().pointSizeF()` back, don't trust the sheet.
  - **A `QDockWidget` draws a title bar even with `NoDockWidgetFeatures`** — nothing in it, ~20px of it, above the panel's own header. The inspector never showed it because it sets its own (`setTitleBarWidget(header)`); the left dock now passes a bare `QWidget()` to get none at all.
  - **The node graph's legend is not in a bar** (`graphLegendBar`, transparent and borderless). Once the zoom cluster moved onto the canvas, the strip above it held only the legend, and a filled band across the whole view for four coloured dots is frame for nothing. It reads over the canvas, like the zoom cluster in the opposite corner.
  - **Zones are separated by tone, not by lines** — VS Code's method, and the thing to keep. Every surface steps at least 3.5 points of L* from the one it touches (`sunken`→`app`→`panel`→`raised`), and `EDGE` — the token the *structural* rules draw with (activity bar, top bar, view toolbar, status bar, splitters, dock headers, panel footers, the tab bar), as opposed to `BORDER`, which outlines a control — is a hint on top of that at 1.05–1.4:1, VS Code's own `#2b2b2b`-on-`#1f1f1f` territory. It went the other way once: `EDGE` was pushed to 1.9:1 so the lines would carry the separation on their own, and the window came out looking like a grid of boxes. `contrast` is the one skin that keeps hard lines (7:1) — there the visible rule *is* the point. `site` derives `app`/`panel`/`raised` from its two brand backgrounds with `_mix` for the same reason: the web's `--bg` and `--bg-elevated` sit 1.08:1 apart, which works on a page and does not on a four-zone window. `tests/test_theme_contrast.py::test_las_zonas_contiguas_se_distinguen` asks for one of the two, never both.
  - Contrast is checked, not eyeballed, in both modes — `tests/test_theme_contrast.py` measures it for every skin and mode: WCAG ratios for text on all four surfaces, L* steps between adjacent surfaces, the edge against each zone, and the dichromacy simulation for the colour-safe skin. It also asserts that the *ordinary* palette still has the red/green problem, so the reason the colour-safe skin exists stays true or the test says otherwise. The pass fixed real defects in the skins that already existed: the site skin's green sat at 2.6:1 on its own white background, and white on the classic purple at 3.5:1 (the accent keeps the brand hue; what changed is the text on it, the way `obsidian` already did it).
