# Semantic engine (dts_engine)

> Detail split out of `CLAUDE.md`. The index and the cross-cutting rules stay there.

**3. Semantic engine (`kernelgrove/dts_engine/`) — no dependencies beyond `dt_model`.** Parses and validates device tree sources; the DB is *injected*, never imported, so `api` can depend on it without a cycle.
- `parser.py` — `parse_dts_source(text)` scans the text character by character (not line by line, so multi-line properties work), tracking line/column and capturing every property. Returns a `ParseResult` with the tree plus syntax diagnostics (unbalanced braces, missing `;` — both after a property and after a node's `}` — and malformed node headers). `parse_dtsi_file` is the thin wrapper the socs ingestion uses.

  **Reopening a node merges into it** (`_open_node`): writing `soc { … }` twice at the same level is one node in DTS, not two, and dtc merges them. Creating two identical siblings — which is what it used to do — splits a node's properties in half, so include merging reached only one of them and the other looked like it was missing `#address-cells`. First occurrence keeps the line and the label.

  Real-world DTS syntax the parser must keep handling — each of these caused hundreds of false positives before being supported, so re-run the corpus check against `kernel/linux/arch/**/*.dts*` after touching it:
  `/include/ "file.dtsi"` (dtc's own include: no `;`), `&{/path/to/node} { … }` (reference by path — those braces are part of the name), chained labels (`vdd_a: vdd_b: node {`), `/omit-if-no-ref/ label: node {` (the directive is stripped in `_parse_node_header`, or it ends up glued to the label), `#define` macros continued with `\`, and the two deletion directives (below). The only known unparseable construct is a node name produced by a C macro (`&DIE_NODE(pmgr)`, `CP11X_NODE_NAME(bus)`) — 11 files, and resolving it would mean running `cpp`; layer-1 checks skip names and labels containing `(…)` for that reason.

  **`/delete-node/` and `/delete-property/` are recorded, not applied** (`DeleteDirective`, `ParseResult.deletions`). dtc removes what they name, so ignoring them — which the parser did — leaves the merged tree holding nodes and properties the compiled binary does not have, and every layer then judges a tree that does not exist. **525 of the 6347 kernel `.dts`/`.dtsi` use them.** The parser only writes down `(kind, target, node_path, line)` because the target is almost never in the file that writes the directive: the real shape is a board including its SoC's `.dtsi` and deleting what it does not carry, so applying it needs the merged tree. `dt_model.model.apply_deletions` does that, and it runs **last** — after includes are merged and after `resolve_label_overrides` has folded the `&label` reopenings — at the three points where a tree is assembled: `IncludeResolver._resolved_source` (each include's own deletions over its own chain, before it is handed to whoever includes it), `KernelGroveService._merged_tree` (the document's own) and `api/overlays.preview_overlay` (an overlay deleting from its base). The target may be a name (`rtc@68`), a label (`&spi0`) or a path (`&{/soc/spi@1}`); a target that is not there is ignored, since claiming it is missing is layer 1's job, not this one's. Known ceiling: all deletions are applied at the end, not in dtc's sequential order, so a source that deletes a node and re-declares it afterwards would lose it — the order that is actually used is declare, include, delete.

  **Never validate using indentation.** DTS has no indentation rules, so any check based on it both misfires on valid files and stays silent on unindented or single-line sources. An earlier version compared closing-brace columns against their node's; it was removed. Use language rules only.

  **Missing `;` — the rule is "every statement ends with `;`"** (`check_statement_terminators`, a line-level pass). The only exceptions are lines that open/close a node (`{`, `};`) and genuine continuations: unbalanced `<>`/`[]`/quotes, a line ending in `=`, `,`, `\` or `:`, a `… = /bits/ 64` whose value is on the next line, a lone `;` on the following line, and the non-statement lines (`#…`, `/include/ …`, `/omit-if-no-ref/`). This catches cases content analysis cannot — a boolean property after another with no `;` has no second `=` to give the merge away. Verified: **0 false positives across all 6330 kernel `.dts`/`.dtsi` files.**

  **Locating a missing `}`.** An imbalance is only detectable at EOF, and which brace was dropped is genuinely ambiguous — later closes silently absorb it. Two honest signals instead of guessing: `/ {` and `&label {` are only legal at the root level, so meeting one while nested *proves* an imbalance and can name what is still open; and at EOF every still-open node is listed, innermost first. Beyond that the editor's brace matching (pure counting) is what localises it interactively.
- `checks/` — the semantic checks, **layered**, in the order fixed by `docs/SEMANTIC-ENGINE-FLOW.md`: (1) Device Tree specification, (2) generic bindings, (3) `dt-bindings/*.h` constants, (4) kernel drivers, (5) the specific binding. Layers 1, 2, (partially) 3 and (partially) 5 are implemented; the order exists so no layer invents a rule the previous one already defines. `checks/pipeline.run_checks(result, text=…, fragment=…, schema_lookup=…, macro_lookup=…, local_macros=…)` is the single entry point (`api/service.analyze_source` calls it).
  - `checks/spec/` — layer 1, one module per block of the spec (`naming`, `properties`, `addressing`, `structure`). Every rule cites its section of the Devicetree Specification v0.4 and none is invented. Severity maps the spec's own language: «shall» → ERROR, «should» → WARNING, deprecated/unenforced limits → WARNING/INFO.
  - `checks/values.py` and `checks/context.py` sit **one level above** `spec/` because every layer shares them: reading DTS values, and the `SpecContext` (own tree + merged tree, property lines, and the policy for when an absence can be claimed).
  - `checks/bindings/` — layer 5. `lookup.py` is the vocabulary (`NodeSchema`, `SchemaProperty`, `SchemaIssue`, the `SchemaLookup` protocol the API implements), `instance.py` encodes a node as the instance a JSON Schema expects, and `rules.py` holds the checks: missing required property/node, property the binding does not admit, value problems, rejected compatible (`incomplete-devices.yaml`), undocumented compatible. It runs **only** when the caller injects a lookup; without one the engine says nothing about bindings. Codes are prefixed `binding-`. **A diagnostic's hint answers the question, it does not restate it**: it used to be the binding's title («ARM Performance Monitor Units»), which the compatible already in the message gives away and which says nothing about the property at hand. Now a missing property carries its type and its enum or first description line (`property_hint`), an unadmitted one names the file that enumerates what is allowed (`schema_file`), and a value problem names the schema that objected **only when it is not the node's own** — half the rules are inherited from the class (`i2c-controller.yaml` and friends) and there knowing it saves the search, while when it coincides it just repeats the message. Layer 2 follows the same rule: its message already names the generic binding, so the hint is the property's type, or nothing. A schema's conditional branches are walked *permissively only*, so a property declared inside an `if/then` counts as admitted but never as required.
  - `checks/overlay.py` — **layer 6**, the only rules that exist because the document is an *overlay*: does its target actually exist in the base it will be applied to. The other five layers already work on an overlay unchanged (it is a fragment like any other — all 361 `.dtso` in the kernel parse with zero diagnostics), so this layer adds only what none of them can see. Same discipline as the rest: **without an injected base it says nothing** — claiming `&i2c0` is missing requires having looked where it should be. Codes are prefixed `overlay-`.
  - `checks/generic/` — layer 2: the 228 schemas dt-schema marks with `select`, which apply by node shape rather than by compatible (device classes, buses, common properties, the vendor-prefix registry). Codes are prefixed `generic-`.
  - `checks/macros.py` — layer 3, two levels. **Existence**, always on: whether a macro-shaped token (`GPIO_HIGH`, `IRQ_TYPE_LEVEL_HIGH`…) is defined anywhere. `MacroLookup` (the injected protocol) answers *is this name known at all*; `local_macros` (plain data, computed by `api/service.py` via `IncludeResolver.macro_names`, which follows the same recursive `.dtsi`/header cascade as `text_in_includes`) says which of those names *this document* can actually see through its own includes. Known-but-not-visible-here is `macro-missing-include` (WARNING, probably a missing `#include`); not known anywhere in `dt-bindings/*.h` is `macro-unknown` (INFO — could be a driver-local macro outside `dt-bindings/`, so weaker evidence). Cheap (dictionary/set lookups), so it runs in `run_checks`, not the deferred pass. **Value**, when the database was built with `cpp` available: the ingestion asks `cpp` to expand every macro name in the real context of its own header (one invocation per header, all names queried at once behind a marker that survives `cpp` reordering lines), then evaluates whatever numeric/operator expression comes back with a small restricted interpreter (`db_manager/macros.evaluate_c_int_expr`) — `cpp` only ever runs at ingestion, against the kernel checkout, never at analysis time or on user text. A function-like macro referenced without arguments (`GIC_CPU_MASK_RAW`) comes back unexpanded and gets no value, though it stays in the existence index. Resolved values feed `checks/bindings/instance.py`: a cell that isn't a plain numeric literal is looked up in `ctx.local_macro_values` (`IncludeResolver.macro_values`, same cascade as `macro_names` but computed only in the deferred pass, since only layers 2/5-values need it) before being given up as uncodable — this is what lets a property like `hisilicon,fixed-mode = <SOME_MACRO>;` actually get validated against its binding's `enum` instead of staying invisible. Doesn't help `interrupts`, though: its matrix shape still can't be encoded without resolving the controller's `#interrupt-cells` (layer 4), a separate, older gap. Backed by `header_macros` (`--table macros`, ingestion in `db_manager/macros.py`): one `#\s*define NAME` regex pass per `dt-bindings/*.h` in the already-populated `sources` table for names (no preprocessor needed there), each header's row set pre-flattened at ingestion to include the macros of whatever it `#include`s in turn (the graph is tiny, 24 edges total), plus a nullable `value` column filled by the `cpp` pass described above.
  - **Two passes, split by cost.** `run_checks` is what runs on every keystroke: layer 1 plus the layer-5 rules that are dictionary lookups (required, unknown property, undocumented/rejected compatible). `run_schema_checks` is everything that means handing a whole node to a JSON Schema validator — layer-5 *values* (≈2.6 ms/node) and all of layer 2 (≈10 ms/node) — and the GUI runs it in a `SchemaChecksWorker`. Measured on a board `.dts`: 17 ms synchronous, 432 ms deferred; on `zynqmp.dtsi` (330 nodes): 155 ms and 2.4 s. `KernelGroveService.merge_deferred` folds the late results in, dropping a layer-2 finding when layer 5 already said the same thing about the same property.
- `diagnostics.py` — `Diagnostic`/`Severity`/`DiagnosticCode`, the shared vocabulary. Layer-1 codes are prefixed `spec-`.

Rules this engine must keep:
- **A layer only speaks about what its source states, and never contradicts an earlier one.** If a check needs something not yet resolved — a macro from a header (layer 3), an include that isn't merged — it stays quiet instead of inventing an error. That's why `values.looks_like_macro_call` exists, and why `_parse_unit_address` only compares plain-hex unit addresses (bus-specific formats like PCI's `dev,fn` are layer 2's business).
- **Claiming something is *missing* means looking at the merged tree, not at silence.** `api/service.analyze_source` merges the document's includes (same `IncludeResolver` the visualizer uses, now with an LRU cache since it runs on every keystroke) and hands the result to the checks as `merged_root`; presence is read there (`SpecContext.effective_properties`/`effective_children`) while the diagnostic's **line always comes from the document's own tree**. Then: document-wide requirements (root `model`/`compatible`, `/cpus`, `/memory`, `/dts-v1/;`) only apply to a non-fragment whose includes are merged (`is_complete_document`); node-level ones always apply, and when the answer can't be conclusive (fragment, unresolved include, an `&label` reopening whose target is nowhere to be found) `report(..., missing=True)` drops the severity one step and says why in the hint.

  **A `&label { … }` reopening is not automatically inconclusive any more.** `_merge_for_analysis` now runs `resolve_label_overrides` on the merged clone, exactly like the visualizer, and `SpecContext._merged_node` falls back to resolving the reference (by label, or by walking `&{/a/b}`) when the pseudo-node's path is not in the merged tree. Without this, every `&ssp0 { status = "okay"; }` in a board file looked like a node with nothing in it: layer 5 alone reported 206 bogus "the binding requires clocks/dmas/dma-names" on a 250-file sample. An earlier version gated all of these behind "no includes at all", which silenced them on essentially every real file — deleting root `model` or a `cpu`'s `reg` produced nothing.
- **Values are judged by the schema, not by the engine.** `checks/bindings/instance.py` translates a node's properties into the instance a JSON Schema expects (a `uint32` is an integer, a `uint32-matrix` a list of lists, `reg` split into rows by the parent's `#address-cells`/`#size-cells`) and `api/schema_validator.py` runs `jsonschema` over it. **Anything that cannot be translated with certainty stays out of the instance** and nothing is said about it: values with `dt-bindings/*.h` macros (layer 3), `&label` references (how many cells each takes is decided by the node it points at), and matrices whose row size depends on another node, like `interrupts` and its `#interrupt-cells`. Of what the schema reports, only *value* keywords are counted (`VALUE_KEYWORDS`) and at most one per property: `required`/`additionalProperties` are covered by the hand-written rules, which know how to look at the merged tree and downgrade when the answer isn't conclusive.
- **A `&label { … }` reopening in a `.dtsi` supports no claim about what's missing** (`SpecContext.is_partial_view`). The binding layers stay silent instead of downgrading: saying "maybe `#gpio-cells` is missing" about a `&gpioa` in a fragment is guaranteed noise, not a reasonable doubt. It was 62 warnings from 4 files in a 150-file sample.
- **Resolution is exact — there is no fuzzy fallback anywhere.** A fuzzy match invents requirements (validating `xlnx,zynqmp` against a PHY binding once produced bogus "missing `#phy-cells`" errors on the root node). `BindingsDatabase.resolve_compatible` is the single route: it tries `bindings.compatible` and then `binding_compatibles`, and returns None rather than guessing. `get_binding_info` now goes through it too — it used to query `bindings.compatible` directly and fall back to `LIKE`, which meant the 20 109 declared compatibles that aren't their binding's *primary* (79% of the 25 458) came back `Unknown` unless some unrelated binding happened to contain the string. `cdns,i2c-r1p14` was one: `Unknown`, no `child_bus`, so `soc_loader._bus_for_node` couldn't see it was an I2C controller. 855 of those non-primary compatibles carry a `child_bus`.
- **Re-run the corpus check after touching a rule** — and run it `--db`, the way the app analyzes (`python scripts/check_corpus.py --db`; `--syntax` for the parser's own diagnostics). Without the DB nothing resolves and the numbers are only comparable to themselves. Same discipline as the parser: every rule is measured against the 6347 kernel `.dts`/`.dtsi` files, which are taken as correct. Current state, over the 6347 files. The two passes are measured separately because the app runs them separately:

Layer 1 keeps dropping as the merged view gets better: 10986 before the dt-schema work, 10079 after folding `&label` reopenings, 9161 once an `#include` written inside a node was merged inside that node, 9137 now that `/delete-node/`/`/delete-property/` are applied. Its errors stayed at 391 throughout, and layer 5 did not move at all when the deletions landed — which is the number that mattered there: pruning the tree could just as easily have *invented* «missing property» on something a board deliberately removes, and it did not. Layer 5's biggest group is `binding-unknown-compatible` (4930 INFO), which is expected — the kernel still has ~1000 bindings in the old `.txt` format that never became YAML, and a node whose compatible has no YAML binding is exactly what that INFO says.

## Trap

- **An `#include` inside a node is merged inside that node.** `IncludeDirective.node_path` carries the path of the node that was open where the directive appeared (the main parser scan records it; the line-based `collect_includes` can't know it), and `IncludeResolver.resolve_tree` merges there. The Raspberry Pi 5 puts its whole RP1 inside a `dev@0` that way; merging it at the root left that node looking empty and produced "the binding requires `pci-ep-bus@1`".
