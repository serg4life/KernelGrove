# Ingestion: from the kernel to bindings.db

> Detail split out of `CLAUDE.md`. The index and the cross-cutting rules stay there.

**1. Ingestion (offline, builds the knowledge base).** `kernelgrove/db_manager/` turns the kernel's `Documentation/devicetree/bindings/*.yaml` schemas into a queryable DB:
`finders.py` (walk for `*.yaml`/`*.yml`) → `loader.py` (parse YAML) → `records.py` (extract `compatible`/`vendor`/`title`, dropping anything that fails `is_valid_compatible`) → `storage.py` (write JSON + create/populate SQLite `bindings` and `socs` tables). Orchestrated by `db_manager/main.py`. During insert, `storage.py` derives `subsystem` from the file path and infers the two bus dimensions.

**Compatible extraction goes through dt-schema** (`db_manager/schemas.py`), not through a hand-rolled YAML walk. The old `extract_compatible` fell back to scraping any nested `enum`/`const` when a file had no `properties.compatible`, and that registered pinmux group names, RISC-V ISA extensions and audio formats as compatibles: 1 161 fake entries and 62 fake `bindings` rows (`iface`, `host`, `pcie`, `gpio30`…). `schemas.top_level_compatibles` asks `dtschema.extract_node_compatibles` for the compatibles the binding declares **for its own node** — falling back to the `select:` block, which is where a binding that leaves `properties.compatible` open declares what it matches — and a file that declares none is simply not a binding (that is what the common-property schemas like `rtc.yaml` are). Declaration order is preserved by intersecting with the ordered walk, because `bindings.compatible` stores the *first* one.

**The `schemas` table is the processed form of every binding** (`--table schemas`, ~90 s): `dtschema.DTValidator(root).schemas`, i.e. what `dt-mk-schema -j` produces — shorthand expanded, types and dimensions normalized, implicit properties (`status`, `phandle`, `pinctrl-*`) injected. It holds all 5 663 schemas, not just the ones with a compatible: `rtc.yaml`, `i2c-controller.yaml` and friends have no compatible of their own but are the target of half the `$ref`s, so without them nothing resolves. `schema_compatibles` records which compatible each schema declares **and in which node of it** (`node_path`), so `ti,twl4030-pwm` resolves to the sub-node of `ti,twl.yaml` instead of to the whole MFD. `schemas.raw` keeps the original YAML because the fixups delete `description` and `examples`, and `schemas.has_select` marks the 228 schemas that apply by node shape instead of by compatible — those are layer 2. `schema_compatibles.position` records where in the node's compatible list each one sits, which is how resolution tells a device's own identity from the generic family it also answers to. See `docs/DT-SCHEMA-INTEGRATION.md`.

**`schemas.since` is the kernel release each binding first shipped in** (`--table kernel`, `db_manager/kernel_versions.py`), and it is the one thing the inspector shows that is written nowhere in the binding: it lives in the repository's history. It is read by **tags, not by history**: `git log --diff-filter=A -- <file>` per binding walks 1.3M commits once per file and never finishes, while reading each release's tree (`git ls-tree`) and keeping the first one that carries each path is 112 tree reads and takes 8 s — and it answers the question actually asked, which is which *release* has it, not which commit wrote it. **The extension is dropped when comparing** (`binding_key`): the mass `.txt` → `.yaml` conversion of 2018-2021 deletes one file and adds another, so matching on the `.yaml` alone dates `serial/pl011` to v5.x instead of v3.10. 5 505 of the 5 663 schemas get a version; the rest are dt-schema's own (`i2c-controller.yaml` and friends live in `dtschema/schemas/…`), and they correctly get none — they are not kernel bindings. The column is added with `ensure_column` and read defensively (`SchemasDatabase._has_since`), so a DB built before it still works, just without versions.

**And it is what answers «will this boot on the kernel I am going to use?»** — `KernelGroveService.kernel_target`, a session setting picked from the status bar (see the GUI section), turns on one layer-5 rule: a compatible whose binding is newer than the chosen release is a WARNING (`binding-newer-than-kernel`). The list offered is `SchemasDatabase.kernel_releases()`, the distinct `since` values, never a hand-written table — a DB built against another checkout reaches exactly as far as that checkout does, and offering a release it cannot check would be promising a check that cannot happen. Same discipline as every other layer: with no target chosen, or no `since` in the DB, it says nothing. And it says only what the datum says: the date is the **binding file's**, not the driver's — a compatible may have existed earlier in a `.txt` binding under another name — so the message is «documented in Linux X» and the hint spells out that caveat rather than claiming the kernel does not support it.

**Bus categorization — `parent_bus` and `child_bus` are independent.** A node can hang off one bus *and* offer another: an I2C mux is `i2c → i2c`, `nxp,sc18is602` is `i2c → spi`. So `dt_model/model.py` keeps two separate tables, `CHILD_BUS_RULES` (`$ref` → bus offered to children) and `PARENT_BUS_RULES` (`$ref` → bus it hangs off), and `infer_parent_child_bus` scans **every** `allOf.$ref` accumulating both rather than stopping at the first hit. Modelling them as one `(parent, child)` tuple, as the old `RULES` did, made every controller look like it sat on `platform`.

`CHILD_BUS_RULES` must have an entry for every bus in `CONTROLLER_LIST` (`i2c`, `spi`, `mmc`, `usb`, `pci`), or a node whose compatible *is* registered in `bindings` (has a `binding_id`) but whose schema isn't mapped here gets dropped entirely — `api/soc_loader._bus_for_node`'s name-prefix fallback (`node.name` starting with `mmc`, etc.) only triggers `if not binding_id`, so a known-but-unmapped binding doesn't even reach it. This is exactly how `mmc` went uncolored in the visualizer despite `mmc-controller.yaml` being the same kind of common `$ref` as `i2c-controller.yaml`/`spi-controller.yaml` — it just had no rule. **This table is read at ingestion, not at runtime**: fixing an entry here only changes newly-built databases (`scripts/build_database.sh`), not `database/bindings.db` already on disk.

When the rules leave `parent_bus` unresolved, `infer_parent_bus_from_examples` reads the binding's own DTS `examples`: a device wrapped in an `i2c { … }` node sits on an I2C bus. The wrapper test is `_example_is_bus_wrapper` — the outer node must have *no* `compatible` of its own while a nested node does. Do not "improve" this by matching the binding's own compatible string: examples routinely use a different model from the same family (the `dallas,ds1307` binding's example declares `dallas,ds1337`), and doing so silently drops those devices back to `platform`.

Storing uses `INSERT OR REPLACE`, which updates rows but never deletes ones that stop being generated — pass `--reset` (as `scripts/build_database.sh` does) to clear the table first, or stale records accumulate across rebuilds.

**2. Editor/generator (interactive).** SoC row in the `socs` table (a catalogue entry: identity plus `file_path`, the key of its source in `sources`) → the source is opened in the editor and parsed → `api/soc_loader.py` keeps only the **controller** nodes of that tree (those the DB gives a `child_bus`, plus names in `CONTROLLER_LIST`) → the PySide6 GUI shows one row per controller with a dropdown of the devices that can hang off its bus → `api/selection.py` assembles an `InternalDeviceTreeModel` exportable to JSON. A tree parsed in the editor can feed the generator directly (`soc_profile_from_tree`) — including a file opened from disk (`_open_explorer_file` → `EditorTab.open_source` → `send_to_generator`), which never touches the DB. `KernelGroveService.load_soc_profile_from_file`/`soc_profile_from_source` were deleted as dead code (nothing called them once that editor-first flow existed); use `soc_profile_from_tree` on an already-parsed tree instead.

## Ingestion and DB-schema traps

- `db_manager` no longer contains a parser: the pure DTS parsing moved to `dts_engine/parser.py` and the old DB-aware `extract_peripherals`/`build_soc_profile` were deleted (they dropped the `child_bus` the DB reported, making every node look like a leaf). `api/soc_loader.extract_connectable_nodes` is the correct replacement. `db_manager` now imports `dts_engine.parser` for socs ingestion — that direction is intentional; never make `dts_engine` depend on `db_manager` or `api`.
- `bindings.compatible` only stores each binding's *first* compatible, so the `binding_compatibles` table maps every declared compatible (~25.4k) to its binding. Resolve through it, or valid compatibles like `cdns,i2c-r1p14` look unknown. It only holds the compatibles a binding declares for **its own node**; the ones declared by sub-nodes (`ti,twl4030-pwm`, `fsl,sec-v4.0-job-ring` — 763 of them) live in `schema_compatibles` with the path of the node that declares them, because resolving them to the parent binding would attribute the parent's requirements to a child device.
- **`bindings.document` is gone.** It held the whole binding YAML (13.6 MB) that nobody read — both callers discarded it — while the same YAML now lives compressed in `schemas.raw`. What's left is `bindings.description`, the binding's prose (1.1 MB), which is what the details panel shows (`KernelGroveService.get_binding_info`). `BindingsDatabase.find_bindings`, the keyword search over that same column, was deleted as dead code. The `search_bindings` that exists today is a different one: the SQL search over `binding_compatibles` that feeds the BINDINGS catalogue. `init_sqlite_db` drops the old column when SQLite allows it and, if it can't, `store_records_in_sqlite_bindings` keeps filling it with the empty string, because in the old schema it was `NOT NULL`.
- **`socs.document`/`boards.document` are gone too.** They stored `parse_dts_source(sources[file_path]).root.to_dict()` — 48 MB of the 120, uncompressed, for a tree that comes out of parsing the source the same row points at. Nobody read it: `SocsDatabase.get_document` → `build_soc_profile_from_document` had no caller, and the real route (picking a SoC opens its source in the editor) parses it anyway. `api/soc_loader.node_from_dict`/`build_soc_profile_from_document` and `KernelGroveService.load_soc_profile` went with them; the tree now always comes from the parser (`soc_profile_from_tree`). Same migration shape as `bindings.document`: `init_sqlite_db` drops the column when SQLite allows it, and `store_records_in_sqlite_devicetree` keeps writing `"{}"` when it can't, because the old schema had it `NOT NULL`. **Dropping a column doesn't shrink the file** — `scripts/build_database.sh` ends with a `VACUUM` for that.
- **`relative_key` must not resolve symlinks.** It used `Path.resolve()` to normalize before computing the relative path, which also follows symlinks — and several `dt-bindings/*.h` are symlinks (`linux-event-codes.h` → `../../uapi/linux/input-event-codes.h`, a few `qcom,*dispcc*.h` aliases). That stored the *target's* path instead of the symlink's own, so no `#include <dt-bindings/input/linux-event-codes.h>` ever found it — 300+ real `KEY_*`/`BTN_*`/`ABS_*` macros invisible to `header_macros` and every gpio-keys node in the corpus flagged as using unknown macros. Fixed with `os.path.abspath` (lexical, doesn't touch the filesystem) instead of `.resolve()`. Some `socs`/`boards` file paths (several Allwinner board variants are symlinks too) were built with the old, wrong key before this fix — rerun `scripts/build_database.sh` to pick it up everywhere, not just in `sources`/`macros`.
- **Processed schemas are tied to the dtschema version that produced them** (dtschema itself refuses a processed file built by another version). `schema_meta.version` records it; rebuild the `schemas` table after upgrading `dtschema`, and keep the `>=2023.9` floor the kernel itself requires.
- **Resolving a compatible is a ranked lookup, not a `SELECT … LIMIT 1`.** Several schemas legitimately declare the same compatible, and picking the lexicographically first one is how a generic `panel-lvds` ended up validated against an Advantech panel binding, inheriting `width-mm = 223` as a required value. `SchemasDatabase.match_compatible` ranks: the binding whose **filename is the compatible** first, then the one that declares it in **first position** of the node's compatible list (`schema_compatibles.position` — a device binding usually declares `[its-own, the-generic-family]`), then a root node over a sub-node.
- **Generic compatibles do not identify a binding.** `simple-bus`, `simple-mfd`, `syscon` and `arm,primecell` are dropped at ingestion when the schema declares any other compatible, otherwise a node's second compatible resolves to some arbitrary binding — a PL011 UART was being validated against a CoreSight schema and told it needed `in-ports`. The first three are dtschema's own rule (`DTValidator.__init__`); `arm,primecell` is ours, justified by the data: 32 different bindings declare it and no other repeated compatible passes six.
